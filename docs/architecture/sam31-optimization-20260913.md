# SAM 3.1 人物融合、传输与响应时间优化

分支：`codex/entity-event-engine`。测试使用既有 RTX 4090 24 GB，未更换实例或权重。
源版本仍固定 `660a5e9e1b8b4c02c0ad97229b88a09a6e4ff5b7`。

## 人物身份与源时间

人脸分支和原生身体分支只在相同 source timestamp、frame sequence 上，以双向唯一的
脸／身体对应关系共享人物编号。先到的脸人物可被第一次原生轨迹认领；双方已经建档时，
可信 alias 会把人物历史、身份、事件、待完成检查归到同一人物。合并不推进 capture
时间、不让旧位置变新，也不重复累计已有事件证据。

多人重叠、明确身份冲突、非 observed 的旧位置、旧 predictor epoch 不能靠几何强行合并。
缺少明确关联证据时仍可能暂存两份人物，不能把本次单人验证解释成通用重新识别准确率。

真实本地 InsightFace 加原片 SAM 返回的复放记录：
`tmp/sam31-real-gpu-20260912/person-merge-real-run2/report.json`。
15 个源帧中 13 帧检测到人脸，最后两帧没有人脸；脸先到和身体先到两种顺序各 16 次状态
更新后均为一个人物。没有修改人脸库，也没有新增远程人脸或事件模型调用。

## 原图、传输与跟踪

事件检查、人脸与源证据保留原始采样 JPEG。远端 SAM 的传输副本可以独立压缩；保留
完整视野、源序号与时间，返回的归一化框继续对应原始画面。压缩在实际客户端请求中计时，
不能把事先离线压缩的成本从实时测试中隐去。

连续模式仍保持同一个原生 session 和 predictor epoch，一个顺序执行槽、最多 16 个待发
采样帧。`SAM31_BATCH_FRAMES=4` 是后续提交触发目标，积压时允许合发最多 16 帧以保持
吞吐；首批仍等待 worker 声明的 16 帧。`SAM31_BATCH_SECONDS=0.5` 缩短后续小批次等待。
统计明确区分 `append_target_frames`、`max_append_frames` 和 `last_request_frames`。

`SAM31_SESSION_HOTSTART_DELAY=5` 将持续待确认输出从 14 帧缩到 4 帧。早期重复／未匹配
淘汰阈值同步取 `min(8, delay)`；三次检测确认规则保留。该配置改变确认策略，需要质量
对照；不能宣称与原始 15 帧配置输出等价。取消、自然 EOF、短首批 final、空 EOF 仍保持
严格已接纳源前缀与有界历史。

## 推理选项

BF16 原本已经开启。新增 `SAM31_COMPILE_MODE=encoder` 仅在严格权重重载后编译固定输入
视觉编码器，保留 complex RoPE，不启用仅适合其他 GPU 的 FA3，不放宽已学习权重验证。
真实 CUDA 预热成功才报告 ready，编译失败不默默回退。

首次实机编译能够运行，但同一 48 帧多人片的每 16 帧推理仍约 2.4 秒，没有证明明显提速。
48 帧的原生 ID 集合一致；358 次人物观测中 13 个框有小幅变化，最大约 2 个传输图像像素；
置信度最大绝对差 0.007761。JSON 不含原始 mask，不能写成掩码逐位一致。

批量后处理通过独立 `SAM31_SESSION_POSTPROCESS_BATCH_SIZE=1|4` 配置。相同 16 帧的三轮
GPU 本机交替实测平均分别 2.2255／2.2293 秒，三轮原生 ID 与 mask hash 均相同，但没有
速度收益。因此当前 Demo 保持 `SAM31_COMPILE_MODE=off`、后处理批量 1。空 EOF 也必须
分块后处理，不能把整个尾部一次塞进容量 4 的缓冲。批量 grounding 没有启用：固定源码
在环形输入、绝对序号及跨 append 缓存上仍有需要单独验证的适配问题。

## 精确源画面展示

active `sam31_stream` 的标注输出改为读取已完成原生跟踪的原始采样帧及该时刻的场景
几何。它等待配置的最小 N 秒及跟踪结果，`stream_delay_seconds` 报告实际延迟；分析慢于
N 时不会将旧框画到实时帧。原始预览继续独立，事件面板保持当前状态，场景时钟不回退。

展示支持与现有 UI 一致的最小延迟 0–30 秒，源元数据最多 512 条，图像仍受原有
512 帧／64 MiB 证据上限约束。已经确证过期或跳过的源会清理，避免 EOF 无效等待。
实际延迟在没有新结果时也随时间继续更新，显式停止后冻结。图像从原有证据缓冲读取；
没有可用精确源时保持原输出
或 buffering。界面选择最新已完成且满足延迟的原始采样帧；同批多帧同时可展示时，
通常跳过较早帧。因此 3 FPS 是送往 SAM 的采样频率，不保证每秒展示三帧，刷新节奏
取决于批次返回与设置延迟。这还不是固定帧率的平滑延迟视频播放器。
自然 EOF 会在关闭场景前有界等待尾部展示；显式停止立即取消，不强行延迟停止。

最终 H.264 GPU 服务联测记录：`tmp/sam31-opt-20260913/service-display-h264/report.json`。
15 帧短片和 48 帧连续片都完成原生收尾，最后展示序号与对应源 JPEG 相符，标记 `exact`，
实际延迟分别约 4.08／5.89 秒，满足测试配置的最小 2.5 秒。该测试验证接线，不是实时
延迟基准，也未调用事件 VLM。

## 实时到达的初始对照

本地 `tmp/rich-benchmark/vtest.avi` 前 48 秒，原生 10 FPS，最近邻重采样为 4 FPS，
192 个源样本。所有实验走同一 SSH 转发与同一 GPU；网络状态会变化，没有统计意义上的
重复试验置信区间。EOF 后追平的零滞后不计作实时表现。

| 配置 | 实时跟踪滞后峰值 | 完成／背压丢弃采样帧 |
| --- | ---: | ---: |
| 原始 JPEG、16 帧提交、确认 15 | 30.50 秒 | 76／116 |
| 在线 512/JPEG65、4 帧触发、确认 15 | 15.50 秒 | 144／48 |
| 在线 512/JPEG65、4 帧触发、确认 5 | 13.50 秒 | 137／55 |
| 在线 512/JPEG55、确认 5、编码器编译 | 12.75 秒 | 144／48 |
| 在线 384/JPEG55、确认 5、编码器编译 | 12.00 秒 | 156／36 |
| 在线 H.264 512/CRF23、确认 5、不编译 | 10.25 秒 | 176／16 |

H.264 4 FPS 的严格固定时钟采样滞后中位数 7.625 秒、P95 9.75 秒，首输出 8.038 秒；
11 次请求全部成功、零源映射拒绝。140 帧在采集期间完成，36 帧在 EOF 后完成。对实际
发送的 176 帧，原图 19,458,007 字节压到 1,495,355 字节，减少 92.31%；不含 JSON 和
base64 外层开销。每 16 帧客户端请求平均 4.437 秒，仍不足以稳定处理 4 FPS。

因此当前 Demo 选择 3 FPS。另一次相同录像前 60 秒测试共 180 帧，全部处理、零背压
丢弃，18 请求全部成功，采集结束后约 4.32 秒完成尾部。固定时钟滞后中位数 6.333 秒、
P95 8.667 秒、峰值 10.667 秒，首输出 10.225 秒。首批仍要积累 16 帧，降低采样率会
延长启动等待；它减少持续积压，不能消除首批确认时间。60 秒一次测试不是长时稳定性
证明，指标也不包含事件 VLM 耗时。

384 分辨率没有被选为最终方案：相同多人片 11.3 秒出现遮挡人物框缩成约 4×3 像素、
邻人框跨越两人的退化；较小的延迟改善不足以支持牺牲定位细节。见
`tmp/sam31-opt-20260913/quality-review/512-vs-384.json`。

H.264 Annex-B 本地原型在 512×384、每块 16 帧、无 B 帧、CRF23 下将同源 JPEG512/55
总计约 4.69 MB 降到约 1.62 MB。每块含源解码、缩放和编码平均约 104 ms，解码约 83 ms；
192 帧数量和顺序完整。这是编解码与字节实验，实际 GPU 端到端表现另行测量。

## H.264 传输接入

生产连续客户端支持 `SAM31_TRANSPORT_CODEC=h264`、`SAM31_TRANSPORT_MAX_SIDE=512`、
`SAM31_TRANSPORT_CRF=23`。原始 JPEG 直接缩放并编码为独立 Annex-B 小片段；无 B 帧、
一个参考帧，每次请求重新带解码头，服务器按数组顺序绑定原始源序号／时间。客户端的
`transport_bytes` 统计真实二进制传输量，包含在总请求时限内的 `compression_seconds`
计入源解码、缩放和编码；历史 JPEG 专用字节计数不会混入 H.264。

协议需要 worker 明确声明 `h264_transport=1`，并由 `SAM31_SESSION_H264_ENABLED=true`
启用；项目通用默认仍是 JPEG。两端固定验证过的 PyAV 17.1.0，worker 在分配解码图像
前检查编码体积、SPS 尺寸、缓冲、参考帧、picture 数量和重排限制。原始请求参与幂等
校验；空 EOF 不附带视频，也不生成虚构帧。编码超时后保留清理令牌，在占用的请求退出
后有界清理远端会话，避免下一次 Demo 启动一直等待 TTL。

同一 12 秒多人片的 48 个原始 JPEG 共 3,942,645 字节，H.264 512/CRF23 传输共
396,393 字节，在线准备合计 0.446 秒。相同 JPEG512/Q65 传输为 1,206,938 字节，
因此 H.264 又减少 67.16%。48 帧的源序号／时间均一致，47 帧人数与原生 ID 集合一致；
基线的 358 次人物观测全部保留，H.264 额外保留一帧将出画边缘人物。对应框 IoU 中位数
0.982，7 对低于 0.75，主要为遮挡与边缘差异；没有人工真值，不能声称准确率不变。
对比记录见 `tmp/sam31-opt-20260913/quality-review/jpeg512-vs-h264512/`。

使用 15 帧项目短片又完成 SAM → 时序事件模型联测：2 次 OpenRouter 请求成功，2 条
判定被接纳，0 请求失败／拒绝。模型请求总耗时 3.891 秒。这是有序录像链路验证，不能
当作实时端到端事件延迟，也没有人工真值可支持准确率结论。

## 可重跑工具

`tools/sam31_latency_run.py` 使用生产 coordinator/client 在线传输，输出源映射、每次
请求、实时固定间隔采样、源到结果耗时、背压覆盖率与 EOF 收尾数量。`--annotation` 在
计时结束后生成全部采样帧的预览：未处理的帧明确标记，不用旧框填补。

`tools/sam31_postprocess_benchmark.py` 在 GPU 本机离线比较后处理 1／4 的交替重复，
剔除上传、源图读取与 hash 计算时间，记录原生 ID、mask hash 和显存。该工具的推理耗时
与实时客户端的总耗时是不同指标。
