# VLM 后端超时与积压：99456091

本报告继续检查 run `99456091-11f7-4d6c-8eb5-5f41c3670c95`，历史结论来自已保存的运行日志、最终状态和原容器部署代码。全部墙钟时间为北京时间。历史分析不依赖新请求；用户授权执行后，本轮已开展请求结构清理与诊断计时改动，A/B 实测和部署结果由本轮执行验证记录另行补充，不能用新版本行为反推旧 run。

## 已证实的因果链

VLM 回答读取耗时长 → 四并发处理能力低于 1.25 次/秒的任务输入 → 事件输入源缓存达到容量上限 → SAM 结果提交等待事件容量 → 两个 SAM 提交位置占满 → 后续 SAM 请求也停止推进，已接纳输入继续排队。

这次不是 SAM HTTP 断流：97 次 SAM 请求（含空的结束请求）均成功，append 全段 P50 0.365 秒、P95 0.877 秒、最大 0.970 秒。append 包含本地记录及网络请求，不能将它等同于 GPU 原生计算时间。124 张接纳的分析源帧最终全部完成跟踪。

## 1. 超时发生在回答读取阶段

121 次 VLM 调用中成功 94 次，超时 27 次。27 次均已上传请求体并收到 HTTP 200 响应头，然后触发 15 秒总时限；没有 JSON 校验错误、连接错误或 HTTP 拒绝。

先只看 94 次成功请求，以免混合成功和超时样本后错误相加：

## 2. 处理容量不足，而不是只有偶发失败

本次 `temporal_observation_fps=1.25`、`max_in_flight=4`。98.400 秒视频产生 121 个时序观察任务，每个通常包含两张图片。

- 从首个 VLM HTTP 请求开始至最后提交，共 356.315 秒。
- 实际终态处理速率 0.340 次/秒，成功观察速率 0.264 次/秒。
- 单次准备与模型耗时之和为约 1,259.85 槽秒。即使四槽完全均匀执行且无额外等待，按本次实际耗时也至少需要 314.96 秒，显著超过视频长度。
- HTTP 在四槽中的时间占用约 87.8%。不是四个线程完全没启动，也不是所有请求被一个共用锁串行执行；各槽使用独立 inspector/client。
- 在最后一张源帧接纳时，仅完成 27 个 VLM 任务，处理进度约到源时间 23.248 秒，输入已到 98.400 秒。

四并发要持续跟上 1.25 次/秒输入，平均每次占槽时间需不超过 `4 / 1.25 = 3.2` 秒，还要留出本地开销与波动余量。本次仅 HTTP 就平均 10.341 秒，即使去掉所有 FIFO 额外等待也不能实时。这里 314.96 秒是按已观测耗时求出的理想容量下界，不是换调度后必然达到的墙钟耗时。

排队优化能减少额外损耗，但无法单独弥补这次数倍的供需差。单纯增加时限会延长失败槽占用；扩队列只会推迟容量触顶，不解决长期实时吞吐。

## 3. 全局顺序提交进一步占住容量

`SceneInspectionWorker._run()` 的可派发容量取 `4 - len(_pending)`；`_pending` 同时包含正在执行和已返回但尚未按顺序提交的任务。`_commit_ready()` 遇到前一个尚未完成的请求就停止。因而后面的快请求完成后，空闲线程可能仍不能接新任务。

实测返回后等待提交：平均 1.106 秒、P95 6.895 秒、最大 11.080 秒。该测点还包含协调器唤醒/调度等待，不能把全部数值都声称为纯队首阻塞。相比之下，事件状态应用平均 0.0045 秒，更新回调平均 0.076 秒、最大 0.637 秒；这些不构成本轮分钟级积压的主要耗时。

进一步对 `backend-phases.json` 的 HTTP 开始、结束、事件提交及 SAM 提交时间作区间积分：

- 在 356.315 秒窗口、4 个槽内，HTTP 总占用 1,251.232 槽秒，未处于 HTTP 的容量为 174.028 槽秒。
- HTTP 已返回但还没记录事件提交的累计时长为 143.925 槽秒；它比 `reorder_wait_seconds` 累计 133.854 槽秒多，主要因为还含状态应用和回调。
- 在“有已跟踪源帧等待 VLM、HTTP 实际未满 4、正在请求＋已返回未提交恰为 4”的区间，累计墙钟时间约 83.841 秒，对应空闲 HTTP 容量约 133.856 槽秒。这与完成结果仍占派发名额的实现一致。

上述积分由日志边界近似重建，含协调器提交/回调和日志开销；HTTP 之外还存在准备工作。133.856 槽秒不是可直接减去的墙钟时间，也不能据此承诺取消 FIFO 就节省 33.464 秒。合理修复方向是分别约束正在执行的请求和有界的已完成待提交结果，同时保留源时间顺序与事件因果关系。

例：源时间 50.512 秒的请求，HTTP 只花 1.806 秒，随后仍等待约 7.82 秒才进入顺序提交。

## 4. VLM 积压已反压到 SAM

最终 scene 的 `tracking_rejections` 为 `inspection_capacity: 1107`，其他跟踪拒绝原因为空。这是同一批结果等待容量时重复尝试的次数，不代表丢弃了 1,107 帧或向 SAM 重发了 1,107 次请求。

部署代码链路：

1. `SceneRuntime._temporal_sources_fit()` 限制待处理源帧/字节；本次待准备/执行任务上限为 8，源缓存数量上限相应为 `64 - 8 = 56`。日志没有进一步区分具体哪一项容量限制先触发。
2. `commit_native_tracking_batch()` 容量不够时返回 `inspection_capacity`。
3. service 抛 `TrackingCommitBackpressure`；SAM 提交循环保留结果、每 0.1 秒等待重试。
4. SAM 请求循环要求“正在提交＋待提交批次 < 2”。两个位置占满后，后续请求也等待。

97 批 SAM append 平均 0.419 秒、最大 0.970 秒；提交阶段平均 1.288 秒、最大 15.137 秒；提交队列等待平均 1.129 秒、最大 14.261 秒。append、提交队列、提交本身三段合计平均 2.836 秒。提交超过 1 秒的批次有 13 个，首次出现在源序号 1094 的单帧批次（提交 1.846 秒，03:41:41.153 完成）。后段原生轮廓输出变慢与该反压链路一致，不能据此归因为 SAM 推理变慢。

## 补查：界面测速约 0.6 秒为何不能直接对应本次耗时

`route_probe.probe_sample()` 从 `chat_completion()` 调用之前计时，到完整响应读取、提取正文、四类事件解析校验结束才停止。因此界面测速是完整响应时间，不是首 token 或仅响应头时间。不能以“0.6 秒只是首字”解释这次差距。

测速与在线请求确实不等价：

| 项目 | 界面线路测速 | 本次持续事件分析 |
|---|---|---|
| 图片 | 1 张固定的 320×180 合成人物示意图，JPEG 75 | 2–3 张实际摄像头图片，本次源尺寸 640×480、JPEG 70 |
| 判断协议 | 原逐帧四事件 grounding，包括对象框与双语描述 | 时序人物事件判断，包括源时间、人物轨迹引用与跨帧动作 |
| 样本与预热 | 每条线路 1 次不计分预热，3 次计分取中位数；图片内容重复 | 连续变化的图片，长期输入，共 121 个任务 |
| 计时 | 完整模型请求与结果校验，不含合成图准备/外层线路排队 | 本文的 HTTP 10.341 秒同样不含本地派发前排队 |
| 服务商约束 | 配置允许按吞吐选择服务商及 fallback，无 provider.only/order | 同一选择后的规则延续到在线请求；不能证明每次实际落到同一服务商 |

输入和协议差异是已确认的测试覆盖缺口，但仅凭像素或提示词差异不能声称已经解释了十倍耗时，尤其前一次真实摄像头 run 的模型阶段也约 1 秒。实际服务商、负载、路由与生成时间仍需等价请求对照。

进一步读取同一持久化数据卷，`/data/selected-route.json` 为内部编号 AA，对应公开线路 C；文件修改时间精确对应 2026-09-18 03:40:28.462。原 run 日志也记录 03:40:11 发起测速、03:40:28.473 手动选择线路成功，03:40:34 开始接纳本次画面。结合部署接线，支持本次使用公开线路 C。该文件后来未改写，重启后的只读路线 API 同样显示保存的线路 C。未读取密钥。

原测速明细只保存在进程内存中，重启后 samples 清空，不能从日志复原逐次计分值。用户随后明确回复：约 0.6 秒的是公开线路 **A**。而本次实际选中的是公开线路 **C**；测速值与运行耗时对应不同线路。代码中 A 对应内部 C（qwen3-vl-8b-instruct），C 对应内部 AA（qwen3-vl-30b-a3b-instruct），是不同模型，不仅仅是同模型的连接名称。未更改用户线路选择。

因此不能将本次解释为“同一线路从 0.6 秒突然变成十几秒”。已确认首先比较了不同模型/线路，其次测速与在线输入和协议也不同。线路 C 本次慢请求、27 次超时及其引发的积压均是实测事实；线路 A 在同样时序输入及四并发负载下是否仍达到约 0.6 秒，尚未实测，不能承诺。

正确的后续对照应固定实际线路与生成参数，用同一组时序输入分别测单请求和四并发，并保留每次完整响应时间、实际路由及脱敏用量。测试输入及并发必须与在线链路一致，才能区分测速代表性、服务端并发退化和运行参数偏差。

初次离线审查的系统提示与元数据样本用匿名合成图片生成，没有模型调用；不是逐字恢复原 run 图片。当时 `scene_inspection.py` 与 `event_sensitivity.py` 在同次 run 的完整部署快照 `.goodvision/diagnostics/frank-stranger-20260918/deployed/` 中分别与修改前工作区文件 SHA256 一致（A057D1AA… / 3F23E975…）；该比对不表示本轮修改后的文件仍与旧部署一致。按图片总字节推算 Base64 时，各图独立 padding 带来至多 4×(帧数−1) 字节误差。字节数、词数均不等于模型 token 数；图片通过 image_url 传输，其 Base64 不能当普通提示词文本 token 计数。

**明确问题是输出要求冲突。** `event_sensitivity.py` 中 smoking HIGH 既要求描述疑似行为，也要求给烟具/动作区域/人物画框；weapon STANDARD/HIGH 也要求画框。`scene_inspection.py` 直接复用这些规则，然后要求“不产生新 bounding boxes”，只输出 `event_label/subject_ids/detected/confidence`。需要保留事件证据和敏感度标准，只去掉单帧检测专属的画框、描述输出要求，避免修改事件含义。旧的单帧接口仍需要其原定位输出规则，不能全局删除。

其他可精简项：窗口起止与各帧时间重复、frame_position/offset 可推导、每个 bbox 重复声明坐标系；`scene_model.py` 在要求 JSON 数组后又追加允许 verdicts 对象包装。可将提示统一为一种输出格式而保持解析器向后兼容。bbox 坐标目前已舍入到六位，没有无限小数问题；本地源框和因果顺序不应因压缩提示而丢失。

没有发给模型的内容包括：完整聊天历史、历史事件判断、全量人物轨迹、SAM mask、人物姓名或人脸库。构造函数固定为 system + user 两条消息，只带当前 2–4 帧及对应人物框。本轮输出响应体仅约 1–1.5 KB；max_tokens 是上限，不能当作每次实际生成数量，也不能仅靠压低上限宣称提速。

同样两帧与相近请求大小，66,666 字节的请求用时 1.806 秒；66,262 字节的另一个请求在 15.029 秒超时；68,864 字节的成功请求用时 14.120 秒。因此数据量大小本身不能充分解释这轮时延差异。提示冲突值得清理，但其性能收益仍需固定图片、线路、并发做原版/精简版对照，当前没有这种在线因果验证。
