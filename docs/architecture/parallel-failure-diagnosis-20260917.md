## 已确认的工程问题

### 1. 显示依赖未经充分验证的轮廓传播

浏览器约1秒后显示画面，而真实SAM锚点平均约3秒才返回。因此多数时候必须将旧轮廓可靠传播到后续画面；现有传播上限只有2秒，且任何顶点局部运动不可信就会拒绝整个人的轮廓。传播并不是一个可有可无的平滑步骤，它是该方案完整描边的必要条件。

真实Chrome、真实Worker／Canvas及正式Python元数据生成与FastAPI路由的离线回放，能在对应原始帧上正确画出轮廓，排除了“接口格式／字符串ID 0／画布完全不通”等假设。运动回放暴露出算法脆弱：早期17张静态自匹配全部通过，相邻真实图仅1/16通过；晚期相邻图0/16通过。

证据限制：服务器保留的是约3 FPS分析JPEG，原浏览器约15 FPS灰度运动链没有留存。因此不能将这些比例当作原run逐帧失败率，也不能逐个解释2927个无描边画面。源绑定可以工作，连续运动覆盖仍未解决；本轮没有靠放宽匹配阈值或强画旧轮廓掩盖它。

此外，元数据请求仅前约42秒有150次HTTP 200完成记录，后约185秒没有完成记录；前端记录87次失败。旧日志未分异常类型，不能断言每次都超时，也没有HTTP 500的证据。两处可复现的阻塞缺陷已在源码修正：

- 状态轮询没有在途限制，阻塞时可不断叠加请求；回归先复现13个并发状态请求，修复为单在途及3秒取消。
- 异步HTTP路由直接执行同步状态／场景快照，可能阻塞同一个事件循环；将这些读取放入FastAPI同步处理池，真实ASGI并发测试验证状态读取卡住时元数据仍可返回。

它们解释了元数据受阻的风险，但原run没有足够的连接占用和锁等待记录，不能把“元数据中断的全部原因”写成已证实。

### 2. SAM再次采样误伤前端已选样本

前端按固定3 FPS源时刻选样，实际摄像头时间有量化与抖动。后端却要求“距上个接纳样本至少1/3秒”，例如一个0.35秒间隔后接0.32秒间隔，后者仍属于下一采样时段，却被再次筛掉。

源码改为固定源时间采样时段，间断后直接跳到下一时段，不补造帧、不突发补算空时段。用归档保留的679个源序／源时间回放：原逻辑接纳515，新逻辑接纳679；模拟完整准备、请求、提交和EOF也保持679个源顺序与时间不变。状态中的682与归档可回放679差3帧，不能声称本次已回放所有682个源。

补查确认679个归档源无重复，515个SAM和567个Face来源均能对应；最后源2938／227.416943秒已归档并完成Face，差额不是停止尾帧缺失。三处源时缺口高度吻合归档层自身的5 FPS最小间隔过滤：距前一归档源约0.131、0.178、0.175秒，均小于0.2秒门槛。该归档过滤是存在的代码行为，但原日志没有记录被过滤源的具体序号／时间，故三帧去向仍不能逐帧证明。归档完整性还需独立审计，不能仅以最终finalized判定没有缺帧。

**该修正尚未部署。** 本次四帧SAM请求平均约1.62秒，所见容量约2.47 FPS，低于真正3 FPS供给。修复错误过滤会暴露更高积压，不能将“少分析所以跟得上”当作性能优化，也不能直接发布后让用户再次遇到不断增加的延迟。采样配置未降低；后续必须验证净处理容量、队列年龄与长run完整性。

### 3. VLM时间窗边界使有效观察被跳过

原代码硬裁最近1秒，又要求2–4张图至少覆盖0.75秒。真实3 FPS四张图常跨1.008秒；裁掉最早一张后剩余跨度不足，于是跳过本来可用的终点。原逻辑对本run源时间及515个SAM输出的重放，生成的148个终点与实际日志逐项一致。

修正仅在窗口跨度不足时保留最接近边界的一个真实前驱，额外范围最多0.75秒，不跨任意长断流。保留最小真实跨度、2–4图、人物真实框、源顺序及新增证据去重；没有降低事件确认门槛。

同一数据离线得到283个不同观察终点，约1.25次／秒。这证明供给缺陷已修正，**不是283次模型成功，也不是事件两秒识别的实测**。本次模型段平均1.36秒，排序等待平均0.083秒；完整事件延迟还包含SAM、证据形成及确认时间。

### 4. 两次模型调用失败缺少具体错误记录

失败源终点为61.346407秒／seq895及72.002808秒／seq1048；原日志仅记录`ModelAPIError`。无法追溯断定是限流、上游HTTP失败还是输出格式错误。不能把这两次失败扩大为全部SAM／Face／VLM停止，也不能因为其余请求成功便忽略用户看到的失败状态。

源码补充安全错误代码、HTTP状态及回归，不打印原始错误正文、provider响应或凭证。VLM日志按固定事件类别分别统计true／false／unknown条目及omitted，区分已验证响应、有效空数组、失败和尚未返回；失败的计数为null，不伪造unknown或clear。这只是响应的事件类别覆盖，不代表所有人物都得到判断，也不代表判定已被接纳；迟到结果仍计0次成功观察。前端补元数据失败分类、Worker排队／完成／迟到及描边覆盖缺失原因，后台仅接纳有界纯数值统计。新日志只改善下一次可诊断性，不能补造本run缺失的原因。

## 吸烟误报及状态延续

本run吸烟配置为`high`，允许基于类似吸烟的行为推断；用户没有吸烟，已核对的初次阳性及确认源图是碰鼻子／脸或抬手，没有可见烟具。本次吸烟报警属于误报，不能以高敏感配置将它解释为正确结果。

去重后的阳性源时共4次：9.680、56.674、125.397、152.006秒，归于同一主体。首次确认来自125.397和152.006两个不同源阳性，相隔26.609秒；中间未知判断保留了阳性计数。没有本次并发提交乱序、重叠终点重复投票或跨人合票的证据。

首次确认后43次不同源状态更新中，34次未知、9次clear；现有规则要求累计10次有效clear才结束，故持续confirmed到停止。这是**模型／提示策略误报与状态规则长时间延续两件事**。源码本轮未将unknown当clear、未偷偷调整敏感度、确认数或解除数；吸烟准确率和长间隔证据累计问题仍未解决。

后续需用无吸烟负例集（摸脸、吃喝、抬手等）和真实吸烟正例对照修改提示与证据协议，并明确阳性累计的有效时间、未知状态及报警可见状态。仅减少误报而不核对漏报，或仅增加调用频率，都不能完成质量验收。
