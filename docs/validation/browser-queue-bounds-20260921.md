# 浏览器补帧队列修复（2026-09-21）

本轮仅修改浏览器显示调度及配套诊断。独立分支 `codex/sam-realtime-queue`，父提交 `914f672`。SAM 模型、worker、时序会话、采样率和服务端调度均未修改；未合入最新 SAM 优化 `46a0924`，等包含该优化的测试完成后再讨论 SAM 结论。没有修改主目录应用代码、操作 8080/8081 服务或租用 GPU。

## 已确认的软件问题

旧版本 a225e44 的 L40S 实验记录浏览器预处理积压 1307 / 1325 帧，元数据应用平均等待 47.56 / 62.18 秒。原视频输出正常不代表浏览器可无限承受后续计算。原实现对每帧直接发送 Worker 消息，底层消息队列没有上限；灰度处理、补帧、描边更新和显示查询经同一有序通道传递，过多旧任务会把后续更新一并阻塞。

依据：[浏览器阶段数据](<D:/Documents/Project Bird/code/goodvision-harness/.goodvision/diagnostics/l40s-video-20260921/browser-breakdown.json>)、[完整实验说明](<D:/Documents/Project Bird/code/goodvision-harness/.goodvision/diagnostics/l40s-video-20260921/DIAGNOSIS.md>)。该旧版本数据可定位浏览器积压，不能评价尚未包含的 SAM 最新优化。

## 修改后的行为

- 原视频仍以 15 FPS 为目标，保留用户配置的 4 秒播放缓冲和原始分辨率；模型在播放缓冲期间照常运行。视频传输、模型输入上传和已经接纳的分析任务不受本轮丢弃策略影响。
- 浏览器预处理与补帧合计最多接纳 2 帧。只有完整计算结束、过期或明确失败才释放名额，灰度处理结束不提前释放。满额时在缩图和分配补帧位图之前跳过新计算；原视频照常保留、播放。恢复后接纳当前源帧。
- 补帧源图从接纳起超过 1 秒尚未开始相应阶段的计算，直接退役；释放位图并返回完成通知。分别在预处理前、补帧计算前检查。正在执行的计算不能被该截止时间强制中断。
- 显示查询最多实际在途 2 个。原图已显示或被播放缓冲淘汰，不等于相应 Worker 查询已结束，不能提前释放名额。
- 描边元数据最多 1 个在途、1 个待发。待发更新合并最多 256 个真实源帧锚点，兼容增量传输；事件快照保持最大已收到版本，旧 HTTP 响应不能恢复已结束事件。保留最早待发时间，避免合并掩盖等待时长。
- 工作线程终止时清理实际待办状态并停止补帧接纳，原视频继续播放。
- 诊断分别记录 `motion_frames_admitted`、`motion_frames_skipped`、`motion_frames_expired`、`motion_metadata_coalesced`；待处理数量读取实际在途集合。新增 `worker_pending_present_queries`、`worker_pending_metadata`。过期帧也在离线诊断重放中保持退役，避免重放制造当时不存在的像素历史。

现有像素对应及断帧保护保持不变，并新增验证：没有目标帧像素或跨越超限时间缺口时不沿用旧描边；新的真实锚点和对应像素到达后恢复。4 秒缓冲中的旧画面仍可使用它自己对应的有效历史。

## 验证

- 215 项 Node 浏览器/补帧/身份事件/诊断重放测试全部通过，耗时 8.53 秒。包含 3 分钟工作线程无响应模拟：2700 张原视频帧全部显示、每张按 4 秒缓冲、待补帧数始终不超过 2；未执行 2698 张可选补帧缩图，实际显示查询仅 2 个积压。
- 1000 次元数据突发只留下 1 个在途及 1 个待发，待发锚点最多 256；新事件版本优先于迟到旧版本。
- 覆盖恢复接纳当前帧、预处理与最终回复乱序、失败释放、过期位图释放、WASM 启动期间过期、断帧后重新锚定、正常计算下 15 FPS 连续描边及原始分辨率和分析 FIFO。
- Python 传输协议、显示协议、诊断校验共 36 项通过（1.67 秒）。`git diff --check` 通过。相关 Python 文件 Ruff 检查忽略已有的 E501 长行风格后通过；未声称整个仓库通过全部静态检查。
- Node 完整结果见同目录 `browser-queue-bounds-20260921-tests.txt`。测试是本地模拟及协议回归，不是真实双路录屏或 GPU 性能验收。

## 后续实测边界

此次修复保证排队数量有界，不能保证主机在任何负载下都达到 15 FPS。显卡像素读取、解码或主线程已有长任务仍可能造成停顿。满负荷时会牺牲部分描边覆盖；如果真实锚点恰好落在跳过的补帧源图上，该锚点不会被错误地套到其他帧。尚未实现从播放位图补回锚点源图或动态降低补帧分辨率。

等另一任务用包含最新 SAM 改动的固定版本完成实验，再统一选择兼容版本做一次双路复测，重点查看原视频新帧率、最长停顿、实际待办上限、描边覆盖、元数据应用等待。对比时明确区分当前分支与测试主分支版本；不在正在执行的硬件对照中途替换浏览器资产。
