# 8080 对外标注视频卡顿与花屏排查

日期：2026-09-21，以下时间均为北京时间。

用户确认消费地址为 `http://192.168.20.116:8080/v1/video/annotated/stream.mjpeg`，接收方在同一局域网。排查对象是对外标注 MJPEG，不是归档录像，也不是控制台连续画面。

初次排查只读检查线上日志、状态、源码和已保存的源帧，并进行本地隔离验证，没有操作线上识别。后续用户补充“不分析时正常，开启描边／分析才异常”，并明确授权修复后部署 8080。下文新增接收缓冲调查；实际部署记录见文末。

## 结论：有两个独立问题

| 现象 | 定位 | 证据强度 |
| --- | --- | --- |
| 正常输入时仍约一秒换一张画面 | 我们的标注输出实现只播放完成 SAM 分析的采样原帧；当前 SAM 配置为 1 FPS | 已确认 |
| 后半段数秒不换帧 | 上游 WebRTC 接收／解码已经数秒不出帧，随后反映到标注输出 | 已确认发生在对外输出之前 |
| 雪花、人物破碎、块状错位和残影 | 未描边源图已破损；本机 UDP 接收缓冲发生过溢出；收包循环内同步转换可复现溢出 | 已确认本机接收缺陷及可复现机制；不能将历史全部丢包归到单次转换 |
| 8080 到接收方电脑的局域网传输 | 没有足够证据认定为主要瓶颈 | 尚未取得对方接收时的逐帧数据，不能完全排除叠加问题 |

因此不能把全部问题归因于外部网络，也不能只提高 JPEG 质量或只修 HTTP 发送。低帧率有程序自身的确定性原因；输入链路还包含本机接收程序，源图已破损并不等于上游摄像头或交换机有故障。

## 追加定位：分析负载与本机接收缓冲溢出

线上主容器网络命名空间的 `/proc/net/snmp` 记录 `Udp InErrors=6222`、`RcvbufErrors=6222`；UDP 校验错误、发送缓冲错误、内存错误均为 0。`eth0` 的错误和丢弃计数为 0，cgroup 的 CPU 限额节流计数与 OOM 计数也为 0。

这证明本机发生过 UDP 接收缓冲溢出，不是仅靠 RTP 序号推测网线丢包。该值是容器网络命名空间的累计值，包含该空间的所有 UDP socket；没有故障发生时的逐 socket 连续采样，不能把 6,222 与最后会话的 821 逐个对应，也不能排除其他环节叠加。容器网卡的零错误同样不能证明外部整条网络无丢包。

对同一输入连接 `8ad64d1502a54de18df55ba1b72a24da`，按日志中的分析运行区间分组，排除边界窗口：

| 指标 | 分析区间之外，197 个窗口 | 分析区间内部，23 个窗口 |
| --- | --- | --- |
| 单帧颜色转换平均耗时 | 4.50 ms | 11.12 ms |
| 定时统计任务调度迟到平均值 | 3.45 ms | 20.76 ms |
| 交接队列等待平均值 | 0.59 ms | 6.15 ms |

同一连接分析期间转换最长 143 ms。另一连接 `263c9d05890a4dd99e382313cee0271a` 的转换平均值也从约 4.24 ms 升至 9.63 ms。上述是自然运行日志的相关性比较，不是保持全部其他条件不变的随机对照实验。更早一条连接在非分析区间也有丢包，因此不能推断“不分析绝不丢包”。

源码显示，`NetworkStreamAdapter._pump_track()` 与 aiortc / aioice 的 ICE、RTP 收包回调共用同一个 asyncio 循环，但直接调用同步 `frame.to_ndarray(format="bgr24")`。转换完成前，该循环无法处理新的 UDP 收包回调。分析增加计算与调度负担时，这个设计会把处理耗时传导到接收缓冲；aiortc 自身的视频解码工作线程并不能隔离这里的额外颜色转换。

安装的 aioice 为 UDP socket 请求 262,144 字节接收缓冲；在同环境新建测试 socket 得到的 `SO_RCVBUF` 为 425,984 字节，受 Linux 记账与上限影响，不等于可容纳的净视频字节数。未修改线上 socket、内核参数或线程数。当前 OpenCV 设置为 16 线程、主进程 93 线程，是资源争用的排查线索，尚无历史栈采样将负担精确归到某个分析模块。

### 使用原接收代码的隔离复现

临时 Linux 容器禁用外网、限制为 2 CPU / 384 MiB，只发本机回环 UDP，不接摄像头、不运行模型。独立发送进程发送 240 个 1,200 字节包，间隔约 0.25 ms；在部署版实际 `_pump_track` 的转换调用中注入 140 ms 等待，接近日志中观测到的单次长耗时。

| 条件 | 收到 / 发送，每次 | 本机接收缓冲溢出增量，每次 |
| --- | --- | --- |
| 原实现，转换无注入等待 | 240 / 240 | 0 |
| 原实现，同步转换等待 140 ms | 185 / 240 | 55 |
| 将相同转换移出收包循环，等待仍为 140 ms | 240 / 240 | 0 |

每组重复三次，结果一致。这验证了该代码位置阻塞会导致同类本机丢包，并验证卸载转换能解除这一阻塞。突发包流量与等待均为人工控制，不能当作修复前后真实摄像头的丢包率测量。

### 本地修复与回归

颜色转换改为 `await asyncio.to_thread(...)`。同一路仍逐帧等待完成，保持顺序，每路最多一项转换任务在执行；没有无限提交转换任务，原有最多两帧的交接队列保持不变。转换后检查停止标记，停止过程中不再发布迟到帧。该修改不能隔离整个进程的 GIL、所有分析线程或解决持续算力不足，后续真实负载仍需观察。

新增回归使用真实 UDP socket：转换被卡住时必须仍能收到包；原实现先失败，修复后通过。同时覆盖转换期间停止／取消、采样顺序、交接队列上限、转换异常清理。接收和连接相关 **36 项通过**；连同此前归档修复的完整相关回归合计 **156 项通过**，只有两条依赖弃用提示。

对实际构建的 `20260921-receive-fix1` 镜像再次运行三轮同一 UDP 突发实验，均为 240/240、缓冲溢出增量 0；使用真实 PyAV 720p YUV 帧验证转换后的 BGR 像素、形状、采样时间和帧序号通过。这一轮没有替换／注入接收方法，实现就是待部署镜像内的代码。

原始证据保存在私有目录 `.goodvision/diagnostics/playback-artifacts-20260921/`：`kernel-network.json`、`analysis-load-comparison.json`、`receive-blocking-probe.json`、`fixed-image-probe.json`。

## 程序自身的确定性瓶颈

部署中的 `service.py`、`scene_delivery.py`、`scene_runtime.py` 所涉及的逻辑：网络帧进入场景后，`TrackedSceneDisplayWorker` 仅登记已接纳的 SAM 采样源；`tracked_display_frame()` 只选择已完成跟踪的源图；该工作线程将结果发布到 `annotated_frames`；用户的 MJPEG 接口订阅这个 FrameBus。

在开始修改接收程序之前，已比对部署源码与本地的 `service.py`、`scene_delivery.py`、`fleet_outputs.py`、`stream_adapter.py`、`stream_timing.py`、`network_display.py`、`video_connection.py`、`result_bus.py`，SHA-256 一致。对 `scene_runtime.py` 的选择语义同时有本地回归覆盖。追加部署准备时，另外对原 health5 的完整 99 个发布文件在两处安装目录进行校验。

## 其他环节与验证边界

- 最近一轮 SAM 的 47 次 HTTP 请求全部 200；请求总耗时中位数 0.607 秒、最大 0.838 秒。此值包含往返和远端处理，不能进一步当作纯模型耗时。本轮没有“某次远端请求卡住近 6 秒”的证据。
- 同一输入连接的预览 JPEG 编码错误为 0，显示编码跳过累计仅 2 帧。输出变稀与输入解码变稀相吻合，不能归为大量 JPEG 编码失败。
- 主容器当前无 OOM 标记，容器重启计数为 0。事后资源快照不能证明故障时没有短暂资源争抢。
- 日志另有约 98,426 条 `Unsupported upgrade request`，以及 12:03:27 一次 STUN 重试回调 `InvalidStateError`。这些应单独清理和核对，但没有证据把它们当作本轮雪花的唯一原因。
- 12:39 的只读现场探测时分析已停止、输入连接错误；本机与局域网地址均取得合法 MJPEG 响应头，之后没有标注帧而超时。停止后的探测不能用于衡量运行期间输出吞吐率，也没有据此认定接口运行时堵塞。

- 描边源选择、生命周期、渲染及跨路输出相关 49 项现有回归全部通过，只有两条依赖弃用提示。测试通过不代表当前“仅输出分析帧”的产品行为满足连续视频需求。

## 修复优先级

1. **先改对外视频输出的生成方式。** 使用独立连续原帧时钟生成标注流，将检测采样频率与视频播放频率分离；按源时间关联标注，延续已有身份、过期和错帧拒绝规则。保留准确采样帧导出语义时，应明确区分出口。不能简单把同一张图重复发送并称作提高帧率，也不能把旧轮廓永久贴在新图上。
2. **治理输入破损。** 已完成本机接收循环卸载颜色转换的针对性修复。真实负载复测时同步记录接收缓冲溢出、RTP 丢包／重传和关键帧恢复，进一步区分剩余的发送端、传输中、接收重组／解码问题。只提高 JPEG 质量或忽略坏帧标志不会恢复已破损的图像。
3. **最后做真实端到端复测。** 不停止识别，分别记录源帧到达、标注发布和对方按 `X-Frame-Sequence` 接收到帧的时间，并保存出现花屏时相同源序号的输入／输出 JPEG。这样才可计算程序处理与最后一段局域网各自增加的延迟。

本次没有改变“只播放分析采样帧”的对外标注流架构，因此收包修复不能自动把该接口提升到连续 15 FPS；这一产品行为需另行实现并验证时间对齐的连续输出。
