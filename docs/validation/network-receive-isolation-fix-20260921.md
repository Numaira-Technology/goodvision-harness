日期：2026-09-21。基于用户拉取 origin 后的 `7c2e723` 工作区，保留已有本地修改。
本轮未启动、重启或部署 8080，未启动摄像头分析；实际协议测试使用不接外网、
不挂载业务数据卷的临时 Docker 容器。

## 拉取后的结论复核

先执行原有接收/时钟相关测试，19 项通过。随后用当前代码重新运行已定时发送的
真实 SRTP/H.264 合成链路对照（2560×720、30 FPS、约 2.49 Mbps、2,467 包）：

| 场景 | UDP RcvbufErrors 增量 | 接收回调收到的包 |
| --- | ---: | ---: |
| 空载 | 0 | 2,467 |
| 业务计算与接收同进程 | 1,506 | 961 |
| 业务计算位于另一进程 | 0 | 2,467 |

因此拉取后结论未改变：同进程计算竞争能够使 UDP 接收不及时，导致本机接收队列
溢出。历史故障的具体证据与边界见 [根因报告](network-receive-root-cause-20260921.md)。
历史采集没有完整逐包记录或线程调用栈，不能由此指认每个丢包或某个具体业务函数。

## 实现

1. `whep_process.py`：以 spawn 子进程执行 WHEP、ICE、SRTP、重组、解码与颜色转换。
   主进程通过一个 32 MiB 共享图像槽取走已解码的完整 BGR 图像；慢消费者只跳过
   完整图像，不阻塞取包。生产者不等待图像复制锁，容量固定，消费者持有独立副本。
   通知使用单个待处理信号量，停止标记使用共享字节，避免等待主进程持有的通知锁。
   支持分辨率变化、正常结束、启动时停止、异常退出及有界的强制回收。
2. `stream_adapter.py`：接入该子进程，保持 LiveFrame 接口。连续 15 秒没有解码帧时
   结束异常连接；停止时通知并回收子进程。接收日志由真正接收数据的子进程输出，
   避免主进程再输出一个全零的同连接汇总。
3. `webrtc_jitter.py`：在单个 aiortc 接收器上安装局部适配层。已越过重组起点的旧包
   不再倒拨起点；保留正常序号回绕与缓冲内乱序。SSRC 切换、同 SSRC 停顿后连续
   序号重启分别处理，并等待 H.264 IDR 恢复。
   重组容量设为 2,048 包，支持实测超过原 128 包容量的大关键帧；缺片挡住后续
   时间戳超过 500 ms 时舍弃该未完成重组并请求关键帧。容量增加不增加正常预取延迟，
   也没有修改 UDP 缓冲或 SRTP 防重放窗口。
4. `continuous_display.py` 与服务接入：SAM 后端的视频展示使用连续采集图像，
   不再只发布被模型采样并完成分析的图像。独立展示缓存最多 512 帧、64 MiB JPEG，
   尊重用户设置的最小延迟与输出帧率；缓存满时保留即将到期的老帧，避免永远无法
   达到最小延迟。保留迟到事件对已展示图像的更新，关闭时清理。

精确轮廓仍只画在对应的原始帧上；短时旧观测使用原有虚线框规则，过期几何不显示。
本次没有虚构中间帧推理结果，也没有实现光流插值。分析较慢时，画面连续性可以改善，
但不等于每一帧都有新轮廓。展示缓存不替代 SAM 的持久证据缓存，不推进分析完成水位。

## 运行观察与验收边界

子进程每 5 秒输出 `network_receive_timing`（解码帧率、PTS、RTP、传输与保护计数）
及 `network_receive_process_timing`（进程 PID、共享交付帧率、覆盖/复制忙计数）。
展示端每 5 秒输出 `sam_display_timing`，带 `playback_mode=continuous_source`。
这些日志不保存视频载荷、凭据或源地址。

每条 WHEP 流预留 32 MiB 共享像素空间，另有解码器内存；每条展示流允许最多 64 MiB
待展示 JPEG，另持有正在绘制和上次展示的图像。超过共享像素容量的输入明确失败。
aiortc 适配使用私有重组接口；升级依赖时必须执行兼容性和真实协议测试。

离线压力测试不能证明真实源网关、物理链路或多路全分析负载下均无故障。
8080 仍需部署后以原摄像头实际验收：至少跨过此前 46 秒故障窗口，对齐子进程
socket drops、RTP 丢包、解码与展示帧率、PTS，以及对方看到的 MJPEG。
没有自动延长既有监控，也没有自动开始新一轮摄像头复测。
