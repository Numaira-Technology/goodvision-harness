## 可复现的问题和修复

### 两支互相等待，且共用远程准入条件

旧混合客户端先启动人脸，再运行安全事件，最后等待人脸汇合：慢人脸拖延安全事件，
慢 LLM 也拖延已经完成的人脸。CPU 单飞使后续窗口经常只有安全事件；远程名额占满时，
整个窗口被跳过，人脸也失去继续确认的机会。

现在安全事件与人脸各有有限任务池：安全事件仍用原并发数，CPU 人脸仍为单飞，
按原采样时钟分别准入。任一支完成即发布；忙碌只跳过自己的实时样本，不排无限队列。
文件分析仍按原有策略等待可用名额，避免丢掉离线待分析窗口。纯人脸模式不新增远程请求。

### 整帧最新优先丢掉了另一能力的有效结果

复现顺序：窗口 0 的人脸阻塞；窗口 1 只完成吸烟阳性并发布；随后窗口 0 的陌生人
阳性完成，被旧整帧最新优先规则判为过时，没有进入实时通道。

现在各分支独立保留最新观测，较晚的人脸结果不会被另一支更新的帧淘汰；同一支
旧阳性仍不能覆盖新阴性。每条消息有独立 `message_id`，保持原帧时间、框和图像，
不把较旧的人脸框贴到较新的吸烟画面。预览不因旧帧倒退。

AnalysisResult v2 Schema 不变。正常混合会话分别发布分支消息，消息中另一支列为
缺失；它不是分支失败。全局最新接口返回源时间最新的一条原始消息，各能力最新接口
分别保留自己的最新观测。SSE 游标按发布顺序递增，跨分支源时间可以交错。
控制台按能力处理时间先后，吸烟当前阴性立即清除吸烟阳性，陌生人结果另行更新。
对接方式与精确图像关联限制见 [接口说明](../../API_DELIVERY.md)。

### 身份确认间隔与日志不足

旧 main 的轨迹间隔上限为 1.5 秒，新功能分支已有 3 秒容忍。用日志中的源时间
66.063、68.406、70.422 秒，输入同位置的三次可靠陌生人观测：旧追踪器的确认次数
为 1、1、1，新追踪器为 1、2、3，第三次确认陌生人。这是**使用真实时间的合成观测
对照**，不是对原摄像头人脸质量的重判。

现在保留检测原始观测与身份稳定后的诊断，区分没有检测到脸、尺寸/质量拒绝、
尚待三次确认、已确认陌生人和沿用轨迹身份。短暂沿用的身份不会被记成新检测证据。
诊断最多列出 8 张脸的框、尺寸、分数、状态和原因，不保存照片、身份名字或特征。
没有降低低清陌生人的可靠性门槛。

### 独立消息不能干扰另一支的事件结束

拆开两支后发现另一个边界问题：人脸消息把安全事件列为缺失，归档若把它解释为
同一时刻安全事件的未知观测，会打断安全事件原本连续的明确阴性。

现在推理登记区分 `safety:<窗口>` 与 `stranger:<窗口>`，缺失只作用于该支自己
负责的能力。实际判断不被过滤；迟到结果及人物重关联仍使用原窗口范围。
两支视频候选共用资源上限，不能因双登记把同一源图算成无限额外缓存。

### 真实 CPU 人脸与受控 LLM 联合运行

使用已缓存的公开 OpenCV 人像 `100032540_1.jpg`，实际检测与特征模型均确认为
`CPUExecutionProvider`（InsightFace 1.0.1 / ONNX Runtime 1.29.0），禁止下载模型，
使用临时空图库。通过真实 `StreamingSession.start/push_camera_frame` 输入，保持
2.5 FPS、6 个安全事件名额和人脸单飞。原尺寸对照为 1618×1522，JPEG 质量 95；
这是高质量确认对照，不是默认 1280/90 输入的性能基准。重复静态人像不代表真实
运动、角度切换或跨人准确率；LLM 的判断和阻塞均由受控替身提供，没有外部模型请求。

首先用空白帧占满 6 个 LLM 名额，然后继续输入公开人像：

- 2.032 秒时 LLM 六个名额全满；在解除阻塞前完成数始终为 0。
- 源时间 2.4、3.2、3.6 秒的三次真实人脸观测形成确认 1 → 2 → 3。
  原图检测脸约 504×738 像素，未放宽陌生人确认门槛。
- 3.844 秒时陌生人阳性已经发布；4.016 秒才解除 LLM 阻塞，提前 **172 ms**。
  从首个高清脸任务开始到首次陌生阳性发布为 1.437 秒。
- CPU 人脸最大并发为 1，繁忙时跳过一个样本，仍完成三次确认。

已安装本地 CPU 人脸依赖的 Python 环境可运行 [联合验证工具](../../tools/face_llm_interop_eval.py)：

```text
python tools/face_llm_interop_eval.py --image <本地清晰人像> --model-root <已缓存模型根目录> --output-directory <新输出目录>
```

模型根目录须包含 `models/buffalo_l`。工具禁止模型下载和外部 LLM 调用，使用临时
空图库，生成逐帧诊断及耗时统计；输出报告已存在时拒绝覆盖。图片须有足够大的清晰
人脸以验证三次确认，否则应视为不满足这个确认对照，而不能降低门槛使测试通过。

独立服务的测试命令如下。`--isolated` 会启动/停止该服务上的测试会话，应使用单独
测试实例；本轮使用临时配置、空图库和临时归档目录，没有对 8081 执行它。

```text
python tools/delivery_smoke.py --isolated --audit-branding --base-url http://127.0.0.1:<测试端口>
```

### 部署后的诊断入口

`GET /v1/status` 的 `pipeline.branches.safety` 和 `pipeline.branches.stranger`
分别显示提交、完成、失败、跳过与在途数，以及最新完成窗口的源时间、耗时和是否
应用到实时状态。`stranger.last_completion.face` 包含：

- `detected_face_count` / `raw_status_counts`：当前帧原始检测，不能用沿用框替代。
- `stable_status_counts` / `reason_counts`：身份追踪后的状态，例如
  `identity_unconfirmed`、`face_too_small_for_stranger`、`extreme_face_angle`。
- `raw_faces` / `faces`：最多 8 个质量与确认摘要。旧客户端不能提供原始观测时明确
  标记不可用，不臆造检测数量。

出现吸烟但没有陌生人提示时，可以据此区分尚无有效人脸结果、忙碌跳样、没有检测到脸、
质量拒绝及尚未确认身份。`last_completion.applied=false` 表示该完成窗口在自己的
分支内已过时，不能直接把它当成能力最新判断。

## 仍需区分的边界

没有可恢复的该次摄像头原帧序列和被丢弃的人脸响应，不能证明旧会话每一次缺失都由
同一原因引起，也没有宣称在那段录像上实测消除了全部漏报。低清画面仍可能没有可靠

执行。受控阻塞测试验证即时性与调度隔离，其等待上限不是生产推理延迟承诺。
