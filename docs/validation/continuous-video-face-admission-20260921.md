## 本轮实现

1. **视频使用连续连接。** `/video/display/frames?continuous=true` 返回长度前缀的
   GVD1 数据流，发送原分辨率 JPEG、源序号、源时间和播放配置，不生成或等待人物轮廓。
   浏览器独立接收字节并通过有界队列解码。跨摄像头代理按流转发，不等待整个响应结束，
   不再受有限响应的 10 秒总超时限制。旧的有限请求方式仍兼容。
2. **描边单独更新。** 浏览器从对应摄像头的 metadata 接口读取增量；未变化返回 204。
   慢请求或失败不阻止视频。增量先筛选新轮廓，再复制对外数据，耗时复制离开元数据锁。
   旧会话、旧裁剪和倒退版本仍被拒绝，姓名撤回和事件时间规则保留。
3. **按播放期限补取。** 不再对所有播放场景只取最近半秒。连续传输允许补取配置播放
   延迟加 0.5 秒范围内的帧，每包最多 64 帧/8 MiB，原后端历史上限仍为 120 帧/32 MiB。
   浏览器待解码队列最多 128 帧/32 MiB，正在解码的一包另受 8 MiB 限制；过期或容量
   超限的显示副本才跳过，并记录 `network_queue_dropped_frames`。4 秒播放缓冲完整保留。
4. **人脸提交离开网络采样线程。** 实时网络会话有一个串行提交工作线程，最多两个候选
   窗口（含正在落盘者），总 JPEG 预算 32 MiB。满额时新候选记录为 dropped/not_admitted，
   不阻塞下一帧及 SAM 供给。已落盘人脸观察仍按原序推理、提交身份和结果；停止先处理
   已排入的候选，再等待原有持久化任务。摄像头上传及离线模式原有完整队列语义保留。
5. **缩短 SAM 提交的主程序锁。** 从私有日志读取已接纳原图在锁外完成；重新取得锁后
   再检查配置版本和协调器身份，过期结果不得提交到新会话。日志可靠性和身份提交原子性保留。

视频没有拿到轮廓时仍播放原画面。轮廓插值只补已有帧上的描边，不伪造遗漏的整张视频帧。
SAM 继续在播放缓冲期间运行，单帧 append 仍延续同一个有状态会话。

## 本地验证与边界

- 144 项传输、跨路隔离、播放、身份、人脸和停止相关 Python 回归通过。
- SAM 锁改动后，56 项 SAM/人脸/服务状态检查通过，包含读取阻塞期间控制锁可用、
  切换会话后拒绝旧提交，以及原有可靠落盘和停止排空检查。这组与前一组有重叠，不相加。
- 浏览器检查覆盖拆包、慢描边时 15 帧照常播放、解码积压上界、断流取消和旧会话隔离。
- 一次 5 秒真实 HTTP 检查：两个合成 15 FPS 源，描边接口每次故意睡眠 1.4 秒。
  两路各收到 76 帧，约 **15.05 FPS**，源序号缺口 **0**，最大送达间隔 **0.188 秒**。
  原始摘要见 `continuous-video-http-20260921.json`。该检查不运行模型，不证明完整应用的
  最终显示帧率、识别准确率或长期稳定性；新版本未追加 GPU 全流程复测。

部署需一起更新浏览器脚本、服务接口、跨路代理和指标校验，重新打开页面。维持 4 秒播放
缓冲及 SAM 2 FPS。视频与人脸供给恢复后，SAM 下游若仍处理不足，不能继续依靠缺帧抑制
积压：实时部署应配合已有 `realtime_latest` 队列策略，并查看过期/替换数与按期覆盖率。
该策略的 1/2/4 帧追加与缓存上限已有独立实验，本轮不偷偷修改 `durable_ordered` 默认承诺。
主程序锁内仍有场景/身份提交和部分写盘；本轮仅移出可安全独立的读取与元数据复制，
没有把“所有锁问题已解决”或“结果延迟已实测下降”作为结论。
