# 纯 VLM 十二路调度与容量测试

此模式只输出场景级 fight、smoking、fall、weapon 判断，不依赖 SAM、
人物框、跟踪 ID 或人脸库。`detected=true` 是模型的场景观察结果，

## 当前验证结果（2026-10-04）

## 请求与队列

- 每路独立进程，默认每秒 1.25 个观察窗口、每秒 2.5 张采样图。
  每个请求包含该路最近 2–4 张图，时间跨度至少 0.75 秒；默认实际为 3–4 张。
  不混合不同摄像头的图，也不把十二路一起拼成一张图。
- `events` 使用原有事件证据规则，输出四项布尔值/null，输出预算 160 tokens。
  单次 HTTP 总期限不超过 5 秒。无需生成描述、人物框或跟踪关联。
- 共享调度器限制总并发、每路并发和请求发起速率。名额优先分配给最久
  没有获得名额的可运行视频路。默认起始参数为总并发 16、每路 2、20 请求/秒；
  这些是待调优参数，不代表提供商已经承诺相应容量。
- 每路只保留一个尚未获得名额的最新观察窗口；新的替换旧的，正在执行的请求
  不撤销。输入图像队列也有上限。超载会减少已完成观察窗口，不能靠丢弃工作宣称达标。
- 等待名额默认不超过 1 秒，且不会为进入分支已超过 3 秒的最新证据发起请求。
  超时、被替换、忙碌跳过均计数。没有无限重试或无界积压。
- 晚到结果仍进入历史记录和结果交付，标记 `historical_only=true`；不得覆盖
  更新的当前状态。消费者按 request_id 去重、按源时间排序，不应把历史阳性
  当成“此刻正在发生”。
- SQLite 中仅存标识和计数，不能存图片、模型回复或密钥。崩溃进程的名额保守地
  保留最多约 60 秒后回收；执行中的正常请求会续租。

## 部署开关

保留现有默认行为。用于纯事件实验时，在部署配置中设置：

```yaml
runtime:
  scene_mode: active
  scene_independent_vlm: true
  scene_vlm_output_mode: events
  scene_observation_fps: 1.25
  scene_max_in_flight: 4
  scene_admission_database: /workspace/vlm-admission/admission.sqlite
  scene_global_max_in_flight: 16
  scene_per_stream_max_in_flight: 2
  scene_requests_per_second: 20
  scene_queue_timeout_seconds: 1
rich_labeling:
  enabled: false
  tracking_enabled: false
  processing_method: null
```

启动时仅选择 `fight,smoking,fall,weapon`，不启用 stranger/人物属性。
多路服务需要按现有 fleet 方式实际配置十二个摄像头服务及容量，不能只把 UI 数字改成 12。

也可使用 `SCENE_ENGINE_MODE=active`、`SCENE_INDEPENDENT_VLM=true`、
`SCENE_VLM_OUTPUT_MODE=events`、`VLM_ADMISSION_DATABASE`、
`VLM_GLOBAL_MAX_IN_FLIGHT`、`VLM_PER_STREAM_MAX_IN_FLIGHT`、
`VLM_REQUESTS_PER_SECOND`、`VLM_QUEUE_TIMEOUT_SECONDS` 环境变量。

**所有进程必须使用同一个 SQLite 文件。** 同机的多个容器需要挂载同一个本地目录；
数据库使用 WAL 日志，`-wal`、`-shm` 文件也必须位于该共享可写目录，不能只挂载单个数据库文件。
等待中的请求只读轮询；实际授予名额时，在写事务内重新检查并发、速率、公平顺序和截止时间。
相同路径名但各自独立的容器文件不是共享调度。不同主机或 NFS 不受此实现支持，
应使用集中式网关/Redis 调度。数据库内的总并发/每路并发/速率配置必须一致；
调参时停止所有参与服务并使用新的数据库文件。不要在运行中删除数据库绕过限流。
关闭时停服务，恢复原 `scene_vlm_output_mode` 并移除共享数据库配置即可。

## 可复现压测

租用新实例后，可直接使用[一键云端测试流程](../guides/vlm-cloud-benchmark.md)：
自动打包上传、安装环境、真实接口探测、逐档压测、条件触发十五分钟持续测试并取回报告。
它沿用外部 VLM API，不需要 GPU 执行推理。

从仓库根目录运行，使用安装了项目、Pillow 和视频解码依赖的 Python。
下列模拟不调用付费 API：

```bash

  --streams 1 4 8 12 --duration 30 --simulated-latency 1
```

真实模型测试先在本地环境配置所选提供商密钥，检查请求预算，再执行：

```bash
INFERENCE_PROVIDER=openrouter .venv-harness-benchmark/bin/python \
  tools/vlm_multistream_benchmark.py --real \
  --video '/Users/bihaotian/Downloads/output 3.mp4' \
  --streams 1 4 8 12 --duration 30 --repeats 2 --plan-only
```

去掉 `--plan-only` 才发起真实请求。可重复传入 `--video`，分别分配给各路。
只有一段视频时会复制为多路，仅验证负载，不等于十二种不同场景的识别质量。
长测试会循环素材。脚本预解码后按真实时间送帧，不降低输入速度，
测量范围排除解码、摄像头上传、SAM 和浏览器显示。

使用同一提供商/模型、视频、采样速度和质量，对照 `--global-limit 0` 与共享调度；
用 `--output-mode full` 对照事件输出简化。`parallel` 每个窗口会发两次请求。
比较吞吐时不可同时运行两组压测。

## 必须逐路读的指标

每次产生 `manifest.json`、`summary.json`、逐路 `reports.jsonl` 和 `status.jsonl`。
保留模型、参数、素材哈希与代码哈希。数据含模型事件判断，按素材访问权限保存。

- 计划观察数、实际完整结果数、及时完整结果比例、各路有效结果/秒。
  分母是固定输入时钟下应观察的所有窗口，忙碌跳过/排队超时也计入缺失。
- 最新证据进入 VLM 分支到结果发布的 P50/P95/P99、模型耗时、排队耗时。
  这不是摄像头到屏幕的完整延迟，也不是事件开始到识别的延迟；
  还需考虑等待足够动作证据的时间。
- 错误数、不确定判断比例、逐路饥饿、输入迟到、是否排空、总并发峰值。
  `analysis_complete` 仅表示字段完整；全是 null 也需通过不确定比例暴露。
- 事件质量必须另评：在统一业务定义的标注集上比较事件 Precision/Recall/F1、
  每小时误报、漏报和事件开始到首次正确报告的延迟。现有 Astra 行为标注是草稿，
  需先对齐动作定义与不确定片段。

最终应先测 1→4→8→12 路，每档重复，然后在十二路持续跑 15–30 分钟并检查
逐路尾延迟/结果新鲜度和事件质量。及时结果期限及通过阈值必须预先明确；
脚本默认 3 秒只是测量参数，不是会议确定的验收标准。

容量粗估：总请求速率 = 路数 × 每路观察频率；所需平均并发约为请求速率 ×
平均请求耗时。十二路 × 1.25 次/秒 = 15 请求/秒；平均耗时 1 秒约需 15 个
在途名额，2 秒约需 30 个，还需要尾延迟余量与提供商限额支持。
限流只能控制排队、公平性和过期工作，不能创造模型算力。
