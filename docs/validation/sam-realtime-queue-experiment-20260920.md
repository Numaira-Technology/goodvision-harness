# SAM 实时队列 worktree 实验

日期：2026-09-20。分支：`codex/sam-realtime-queue`。基线：`bf614ae14720923bcec68db4354a6d2398d33633`。

## 结论

已完成首版可开关实验。保持 4 秒视频播放缓冲、同一 SAM 时序会话和三次真实检测确认；未修改 GPU 引擎、模型、压缩参数、播放代码或部署环境。批次上限可选 1/2/4，不把“单帧可执行”等同于“单帧更优”。

有界候选能在模拟过载下减少排队，但过早丢帧会降低结果及时覆盖率。第二轮扩大候选窗口后缓解了损失，仍未证明生产描边率不退化。因此新策略默认关闭，仅用于对照，不推荐现在直接替换正式配置。

主目录未提交的云端、GPU 显存和交付修改没有复制或修改；此 worktree 从上述已提交版本开始。后续集成应单独核对这些并行改动。

## 单帧追加是否可用

真实日志中 394 个数据请求有 316 个单帧请求，全都返回一帧且成功；末轮单路会话 72 个请求有 69 个单帧请求，native 会话累计帧数继续增长至 76。这不是新测试成绩，只是本次已收集日志提供的兼容性证据。

`SamLiveContinuation.run()` 复用 `session.native_state`，只在首次创建时初始化。`CausalPostprocessing` 按到达顺序逐帧调用 native inference。因此“追加一帧”不清空历史，也不把视频模型改成无状态图像检测。原三次检测确认不变。

新增测试覆盖同一生产 adapter 在 1/2/4 帧分组下保持状态、源顺序和确认标记；底层算子使用测试替身，不能证明真实 GPU 的质量等价或速度相同。跳帧导致的快运动、遮挡后 ID 连续性仍需实机质量对照。

## 本次改动

- `realtime_latest` 限制尚未准备候选的数量与年龄；满额替换最旧候选，超时可在没有新帧到来时主动过期。
- 实际 append 上限可选 1/2/4，空闲立即提交可用帧，不为了凑满批次延迟第一帧。
- 实时模式不在前一请求长时间执行或提交受阻时过早冻结下一份媒体；已准备但过期且从未发送的整个批次可以退役。
- SQLite 原子保存跳过的源序、源时、会话和原因，再释放该 SAM 私有图像副本；已发送或可能执行的请求不能被此机制丢弃。
- 已返回的真实结果与提交所需证据保留；提交背压重试不产生额外推理。处理完空候选会话时，不影响正在切换的新 run。
- 状态接口新增策略、实际批次上限、跳过原因、待发年龄、最新结果年龄以及 4 秒截止时间的及时率。
- `durable_ordered` 默认行为保留。无帧被送入模型就因过期结束时，正常关闭空会话，不伪造 EOF 源帧。

## 双路模拟对照

两套真实协调器、真实 HTTP 客户端和现有 `FairGPUAdmission`，共享一个执行槽。输入为每路 4 FPS、采集 7 秒；模拟模型每帧正常 0.03 秒，在第 1–5 秒变为 0.60 秒，然后恢复。候选策略之外采样时钟相同。每配置只运行一次，结果受线程调度影响。

**这是可重跑的协议/调度实验，不是 SAM GPU benchmark。** 图像和模型结果是替身；没有测量人数召回、轮廓质量或真实浏览器描边率。实验 4 FPS 不是本次部署的 1 FPS。

| 配置 | 两路最坏源到结果 | 4 秒内完成 / 全部输入 | 采集期完成帧数（共 56） | 两路最长无新结果间隔 |
| --- | ---: | ---: | ---: | ---: |
| 原有 FIFO | 5.02 秒 | 45/56（80.4%） | 29 | 3.05 秒 |
| 4 候选 / 2 秒 / 1 帧追加 | 2.24 秒 | 36/56（64.3%） | 36 | 1.41 秒 |
| 8 候选 / 3 秒 / 1 帧追加 | 3.19 秒 | 44/56（78.6%） | 44 | 1.38 秒 |
| 8 候选 / 3 秒 / 2 帧追加 | 4.12 秒 | 41/56（73.2%） | 42 | 2.41 秒 |
| 8 候选 / 3 秒 / 4 帧追加 | 4.64 秒 | 38/56（67.9%） | 43 | 3.64 秒 |

原 FIFO 最终把 56 帧处理完，其中许多在停采后完成；“4 秒内完成”按每个源的真实接纳时间计算，允许在其截止时间内收尾，采集期完成量另列。新策略的分母包含跳过帧，不用“处理过的帧全部及时”掩盖覆盖损失。

第一轮小窗口证明“尽快丢旧帧”并不等于最优。第二轮 8 候选/3 秒/单帧追加把最坏等待降至约 3.2 秒，及时率约 78.6%，接近 FIFO 的 80.4%，但仍少一个及时源帧。该结果支持继续按播放预算选窗口，不支持宣布任何配置已经达到正式质量门槛。

`admitted_deadline_coverage` 是从 Harness 接纳到提交完成的及时率；**不是 actual contour_frame_ratio**，也不包含输入接收前的 PTS 落后。真实播放覆盖还取决于输入、轨迹质量、几何传播和浏览器呈现。录屏和显示指标必须另行验收。

## 配置与复跑

仅从此 worktree 构建/启动的 Harness 才含新功能。给原有旧镜像添加变量不会获得这些改动。无需改变现有 Contour 媒体协议；保留当前服务器、压缩、采样率和 4 秒播放配置。

| 环境变量 | 默认值 | 作用 |
| --- | --- | --- |
| `SAM31_QUEUE_POLICY` | `durable_ordered` | 设置 `realtime_latest` 才启用实验，仅支持 sam_live |
| `SAM31_REALTIME_APPEND_FRAMES` | 1 | 实际追加上限 1/2/4；仍在同一会话中推进历史 |
| `SAM31_REALTIME_PENDING_FRAMES` | 2 | 未准备候选数 1–8；不是整个管线的总帧数 |
| `SAM31_REALTIME_MAX_AGE_SECONDS` | 2 | 未发送候选年龄上限，按播放缓冲与算力调整 |
| `SAM31_RESULT_DEADLINE_SECONDS` | 4 | 及时率测量截止时间；不修改播放缓冲，也不强杀已执行请求 |

等待池之外仍有至多一份准备工作、一份在途请求和两个未应用结果；它们各自有界。已开始准备的工作须先退出准备，再检查过期；在途请求不能被上述年龄上限抢占。此阶段还没有节点许可或 GPU 内部过期取消，因此结果延迟没有硬上限。

下面是双路 1 FPS 实机对照可选起点，**并非已经选出的最优配置**。先运行原策略基线，再分别改追加上限为 1、2、4；所有测试保持 4 秒视频缓冲。

```powershell
$env:SAM31_QUEUE_POLICY = 'realtime_latest'
$env:SAM31_REALTIME_APPEND_FRAMES = '1'
$env:SAM31_REALTIME_PENDING_FRAMES = '4'
$env:SAM31_REALTIME_MAX_AGE_SECONDS = '3'
$env:SAM31_RESULT_DEADLINE_SECONDS = '4'
```

回退为 `SAM31_QUEUE_POLICY=durable_ordered`，在服务启动或新会话边界生效；不要改写运行中的请求内容。丢帧审计保留在原 SAM 私有 spool 中。

本地模拟运行（需仓库开发依赖，PYTHONPATH 指向本 worktree 的 src 与根目录）：

```powershell
py -3.12 tests/benchmark_sam_realtime_queue.py --pending-frames 8 --max-age-seconds 3 --output docs/validation/sam-realtime-queue-buffered-synthetic-20260920.json
```

## 验证与后续门槛

本轮定向回归 **289 通过、1 跳过**。范围包括新策略、原有 FIFO、配置、生产会话 adapter、双路 FIFO、源映射、提交背压、HTTP 重试、H.264 协议与原显示路径。跳过项为需要 PyAV 的实际 H.264 客户端/worker 组合测试，本次 Python 环境未安装 av。改动文件 Ruff 静态检查和 `git diff --check` 通过。

新一轮 GPU 测试和浏览器播放测试尚未执行；没有用模拟结果替代 GPU 成绩。正式启用前需完成：

1. 固定原片与输入采样，基线和 1/2/4 档分别至少 3 次，再做双路 60 分钟。
2. 同时记录 native、GPU 等待、前端等待、结果及时率、实际 observed/propagated contour_frame_ratio 和最长无轮廓间隔。
3. 对照快运动、多人遮挡、进出画面和短事件，检查人物召回、ID 切换、确认/解除、原始证据保留。
4. 按请求补齐显存/活跃对象/历史状态指标，继续查 native 从 0.4 秒涨到 4–5 秒的原因。队列优化不会增加 GPU 的物理算力。

重点帧预留、基于事件的优先级、节点统一调度、自适应采样、接收侧积压修复与 GPU 内部优化尚未实现。首版试验的目的，是在保留视频缓冲和模型历史的前提下，把队列取舍变成可验证、可回退的参数。
