# VideoJev GPU / 精度对照 · 第一轮实机记录（2026-11-22）

PR #123 的证据。问题是：Qwen8B 上"换卡提速明显、换精度不影响准确率"的结论，对 VideoJev 是否也成立。

## 结论
1. **FP8 不值得用。** 在同一台机器上和 BF16 比：
   - **4090：** 吞吐量提高 3%，决策阶段快 5%。
   - **L40S：** 反而变慢，吞吐量下降 11%，决策阶段慢 15%。
   - **好处：** 唯一明确的好处是显存，从 9.6 GB 降到 7.1 GB。
   - **原因：** 原因和事先预计的一致。没有 `torch.compile` 时，动态 FP8 每次调用都要先量化一次激活值；4B 模型的矩阵乘法又小，这部分开销把收益吃掉了。
2. **换卡的收益没法干净测出来，大概在 1.1 到 1.3 倍。**
   - L40S 比同一轮的 4090 快 7%（第二次尝试）或 29%（第三次尝试）。
   - 两次结果差这么多，是因为同样是 4090，两台主机的吞吐量差了 19%（11.0 和 8.98 个窗口/秒），和卡型之间的差距一样大。
   - 和 Qwen8B 的 2.1 倍差得很远。
3. **准确率不受影响。** 202 题里，FP8 和 BF16 只差 −0 到 +3 题，方向不固定。
   - **答案改变：** FP8 改变了约 20 个逐窗口答案，是换卡（约 10 个）的两倍；概率漂移 P95 为 0.056，换卡为 0.026。
   - **改变的是不是临界题：** 被改的答案里只有 1–2 个不是临界题，baseline 里前两名的概率差最多 0.18。换卡改变的答案，前两名差距全部小于 0.1。
4. **时间花在哪。** 12 路并发时 GPU 已经满载，每个请求 60–70% 的时间在排队。
   - GPU 上大约四分之三是语言模型的决策阶段，0.22–0.28 s。视觉编码 0.06–0.07 s，预处理 0.01–0.03 s。
   - 要真正提速，得从决策阶段本身下手，比如更大的 batch、`torch.compile`、减少问题数，而不是换卡或换精度。

## 版本与环境
- **代码：** `07b0712`（分支 `claude/videojev-fp8`）。服务是**当前的** `goodvision_harness.videojev_service`，不是冻结跑分用的历史服务。
- **模型：** `ZhuYuhan/VideoJev-4B` @ `1c1a253b`，权重从 R2 拉取。
- **环境：** 镜像 `pytorch/pytorch:2.8.0-cuda12.8-cudnn9-devel`；装 torch 2.8.0+cu128、transformers 5.14.1、flash-attn 2.8.3.post2，FP8 另装 torchao 0.13.0。依赖见 `tools/videojev_probe/requirements-fp8.txt`。
- **服务参数（四次运行完全相同）：** `--ready-capacity 4 --gpu-batch-size 4 --max-pixels 409600 --prefix-cache --cpu-threads 4 --request-timeout 20 --queue-age 19.5 --queue-capacity 48`。只改 `--quantization`。
- **FP8 范围：** 语言模型里的 125 个线性层（MLP 和全注意力层的投影），按张量缩放。见 `docs/guides/videojev-fp8.md`。

## 方法
- **数据：** unified-frame-202-v1 的测试集，202 题、2037 个窗口、192 段视频。每个窗口取 2 帧，间隔 1 秒，用冻结的 6 个问题。bundle 由 `07b0712` 的 preflight 离线生成，只放在评测机上，不进仓库。
- **工具：** `07b0712` 版本的 `tools/unified_benchmark/gpu_sweep.py`。Frank 在 `341c08a` 里把它移到了 `tools/videojev_probe/gpu_sweep.py`，并收紧了比较条件：新增工具自身哈希、预热次数、全新服务进程等检查。本轮的 `run.json` 早于这次修改，新版 `compare` 会以 `sweep_sha256` 不一致为由拒绝；表里的对比都是用 `07b0712` 的 `compare` 算的。之后再跑请用新路径。
  - **客户端：** 在 GPU 机器本机运行，避免把网络延迟算进去。
  - **并发：** 12 个视频 worker，同一源最多 1 个在途请求。
  - **发送：** 每个单元只发一次，不重试。正式计时前先发 3 个不计分的预热请求。
  - **计分：** 准确率用冻结的计分器；延迟按 nearest-rank 计 P50/P95，只统计成功的单元。
- **baseline：** 同一台 4090 上的 BF16。FP8 和同机的 BF16 比，L40S 也和这台 4090 的 BF16 比。另外附上 L40S FP8 和 L40S BF16 的同机对比。
- **启动：** 用 `start_sweep.py` 租机、装环境、拉权重、依次跑 BF16 和 FP8，然后拷回结果并释放。用法写在文件开头；凭据只通过 SSH stdin 传，不进仓库。

## 局限
- **每种卡只测了一到两台主机。** 同型号的 4090 在不同主机上差了 19%，所以换卡的效果只能给区间，不能给一个准确的倍数。L40S 两次都是非数据中心主机，CPU 也不一样，预处理时间相差约 3 倍（0.011 和 0.031 s）。
- **没测 `torch.compile`、更大的 batch，也没测 H100、A100。** H100 和 A100 要另打环境包（flash-attn 要按 sm_90 / sm_80 重新编译），A100 只能跑 BF16。
- **不代表 12 路摄像头的实时吞吐。** 这只是冻结帧的回放，每个窗口 2 帧、间隔 1 秒。线上实时用的是间隔 0.5 秒。
- **不是冻结跑分结果，不能写进跑分表。** 这里用的是当前服务，冻结跑分用的是历史服务和它的协议。

## 失败的尝试（如实记录）
- **第一次尝试：** 两台机器都在跑分前停下，原因是 bundle 生成之后 `gpu_sweep.py` 又改过，bundle 记录的源码指纹对不上，校验拒绝运行。没有产生任何测量数据，花费约 0.40 美元。
- **第二次尝试：** BF16 跑完后，脚本卡在停 BF16 服务这一步。非交互 bash 里的后台进程会忽略 SIGINT，我的 `kill -INT` 不起作用，最后等到 2 小时超时才自动拷回结果并释放。BF16 的结果完整保留，就是上表里标"第二次尝试"的两行。花费约 2.75 美元。之后改成先发 TERM，60 秒内不退出就强制 KILL，并把超时缩短到 50 分钟。
- **第三次尝试：** 正常完成，约 0.45 美元。
- **合计：** 约 3.60 美元，所有机器都已确认释放。
