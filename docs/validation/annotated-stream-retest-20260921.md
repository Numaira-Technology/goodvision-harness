# 8080 雪花复测：网卡到包与应用丢包对照

日期：2026-09-21；以下表格均为北京时间。使用已部署的 `20260921-receive-fix1`，本轮只进行被动监控，没有重启、改配置或部署新版本。

## 结论

这轮雪花的主要丢包点已定位到**本机应用 UDP 接收缓冲**。网卡侧视频包大体完整到达，同一个视频 socket 却持续溢出；丢包增长与用户报告的“开始后 16 秒出现、19 秒加重、26 秒满屏”吻合。

前一版将颜色转换移到线程解决了一个可复现的阻塞点，但没有解决真实分析负载下的接收能力问题。不能再以隔离转换测试通过推断真实摄像头花屏已修复。

本轮能够确认应用接收跟不上，尚不能只凭 CPU 总量和线程 ID 判断究竟由哪一个分析模块、GIL 争用、接收回调开销或锁等待主导。需要函数／调用栈级采样才能进一步分摊，不能直接把所有耗时归给描边模型。

## 监控方式

14:00:52 开始最多 30 分钟的只读监控：

- 每秒读取容器网卡字节／包数、UDP `RcvbufErrors`、应用 UID 对应各 socket 的接收队列和丢包计数、CPU 使用量及各线程 CPU、内存、CPU／磁盘压力。
- 单独的低优先级进程在容器 `eth0` 被动读取 IPv4 UDP / RTP 包头，仅统计本应用当前 UDP 端口。按源地址、端口、SSRC、payload type 区分流，统计序号缺口、迟到补回、重复包、包量与字节数，并记录采集 socket 自身丢包。不保存视频载荷。
- 每两秒读取应用状态，与已有约五秒窗口的接收／显示／归档日志对齐；实时保存服务日志。
- 14:04:36 补充 Windows 网卡计数和路由采集。这部分晚于本轮故障，因此不能用它事后的零错误证明故障时无线链路无异常。
- 当前视频实际来源为 `192.168.20.198:8000`，RTP PT 101，SSRC 7141453，接收本地端口 58169。主机路由查询显示经 Wi-Fi 直连。源网关地址与此前示例接口地址不同，判断以实际包头为准。

采集不会启动／停止识别，不连接第二个摄像头会话，不发送探测视频包。监控自己的包头 socket 在本轮 **丢包为 0**。系统计数采样耗时在运行分析时最大约 62 ms，在非分析时最大约 42 ms，实际采样间隔约一秒；CPU 指标包含同容器内的小量采集开销。

## 网卡侧与应用侧的差异

分析运行区间附近，包头监控记录 86 个新序号缺口，其中 74 个后来补回，留下约 **12 个未补回序号**；采集本身丢包 0。与此同时，应用 socket 丢掉 7,452 个到达本机的 UDP 包，足以排除“主要是在外部网络丢掉这些包”的解释。

还出现 **5,083 个相同流序号的重复包**，与故障后重传增多相符，但包头监控没有读取加密反馈内容，不能把每个重复包都独立证明为一次 NACK 重传。本机丢包数包含原包、重复包等，因此不能把 7,452 当作独立视频序号损失数，亦不能与接收端 RTP 净丢包率直接相除。

原视频入站约 3 Mb/s，故障区间容器总入站采样峰值约 8.22 Mb/s；总出站峰值约 15.42 Mb/s。未观察到足以认定网卡带宽耗尽的证据；Wi-Fi 标称速率本身不能证明可用吞吐量。核心证据是同一时段网卡能看到包、应用 socket 却溢出。

## 程序负载与尚未分摊的慢处理

- 开始分析后的短时 CPU 峰值约 **8.66 个核心**，此前通常约 1 个核心；后半段严重丢包时仅约 2–4 个核心。Docker 可见 16 个 CPU，没有 CPU 配额节流证据，不能称为“整机 CPU 一直跑满”。
- 应用线程从非分析时的 109–125 个变为分析时的 121–138 个。线程 ID 能反映竞争随分析出现，但 Linux 线程名相同，不能据此确定具体 Python 函数。
- 输入颜色转换虽已卸载出接收循环，在分析时仍明显变慢，单次最大约 292 ms。这是负载影响的表现，不能仅凭耗时再次断定它独占事件循环。
- 同一轮归档日志还记录一项 `frame` 处理 **19.37 秒**、一项 `window` 处理 **23.21 秒**，随后一个入队项等待 **50.48 秒**。此前归档修复仍未覆盖当前真实负载下的全部慢处理，仍需继续分摊等待与计算；这些整项耗时并不等于持续持有 GIL 的时间。
- SAM 接口仍持续返回结果，39 个接纳帧、193 个采样跳过、背压丢弃 0；不能把采样跳过直接当作网络丢包。
- 对外标注流本轮 38 个不同源图、14 次同源重画，日志不同源帧率约 **0.765 FPS**。这仍是另一项输出生成限制，与本机 UDP 丢包分别处理。

后续修复方向应优先保障接收与解码不受分析进程内的竞争影响：结合调用栈采样定位重负载，并验证独立接收进程或其他接收隔离方式。单纯加大 socket 缓冲只可能延后满溢，不能未经持续负载验证就认定解决问题；只提高 JPEG 质量也无法修复已损坏的源图。
