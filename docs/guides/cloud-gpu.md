# 云 GPU 多路追踪

云 GPU 使用与本地部署相同的 N 路主程序结构，不再限制为一路视频。
`--streams N` 是实际创建的视频通道数，没有固定产品上限；可处理的实际路数、
采样帧率和延迟仍取决于显存、算力、网络和主程序所在机器的资源。

## 启动和使用

在 `.env` 中保留现有 `VAST_API_KEY`、`HF_TOKEN`、`SAM_SSH_KEY`。
启动 37 路主程序和云 GPU 控制器：

```powershell
python tools/start_cloud_gpu.py --streams 37
```

此步骤只启动控制台，不创建付费云实例。`--dry-run` 可查看部署计划，
不会调用 Docker、租卡或修改文件。

1. 打开主程序控制台，将“人物追踪运行位置”选为“云 GPU 服务器（多路）”，保存默认设置。
2. 在云 GPU 区域输入型号 `A100`、数量 `5`。也可填写具体型号，例如 `A100_SXM4`。
3. 可以展开“编辑租用脚本参数”直接编辑 JSON。界面显示根据配置生成的实际启动命令。
4. 点击“启动租用（开始计费）”。页面先保存参数，再启动当次租用，等待所有 GPU 就绪。
5. 添加并连接视频，然后开始全部分析。
6. 改型号或数量前，停止全部分析，点击“释放云 GPU”，再修改和启动。

保存租用配置本身不会租卡。参数保存在 `cloud-gpu-settings` Docker 数据卷；
关闭浏览器不会释放 GPU。停止云控制器/Compose 应用会请求释放当前实例。
原 `compose.yaml` + `compose.sam31-remote.yaml` 入口也改为在 UI 明确启动租用，
其默认仍部署 1 路主程序；多路请使用上面的启动器。
原先保存为 `legacy` 的受管云端追踪配置会自动迁移到 `cloud`；
其他本机/独立服务器设置保留。普通旧版外部单会话服务仍保留其兼容入口。

视频通道数必须与主程序部署一致。扩容时重新用 `--streams N` 启动，
再保存云 GPU 配置中的相同路数。各路主程序有独立的数据卷，只有主控制台开放端口。

## 多卡工作方式

租用查询使用精确 GPU 数量，例如 `num_gpus=5`，在一个实例上寻找五张匹配的卡。
`A100` 匹配内置 A100 PCIe/SXM4 型号列表；具体型号按输入精确查询。
没有匹配机器时会报告失败，不会改租其他型号或八张卡。
市场查询语法见 [Vast 官方 CLI](https://github.com/vast-ai/vast-cli)。

每张 GPU 启动一个模型进程，以 `CUDA_VISIBLE_DEVICES` 隔离。
视频按序号轮询分配：第 1–5 路分别使用 GPU 0–4，第 6 路回到 GPU 0。
同一路的创建、追加、健康检查、结束请求始终使用同一进程、同一通道，
模型时序状态不会跨 GPU 迁移。每张卡内部的多路会话保持独立并公平排队。
不同卡可以同时推理，启动就绪需要所有卡都通过检查。

增加 GPU 数量主要减少多路并发时共享 GPU 的排队。单路时序追踪仍在一张 GPU 上运行，
不能将五张卡的显存或计算简单合并来保证单路五倍加速。
本次修改未实际租卡或测得 A100 上的 Contour 延迟；需要用真实视频验证吞吐和延迟。

## 失败与清理

原有启动失败重试和释放流程保留。控制器持久记录本次实例 ID 和唯一租用标签。
若创建结果不明、释放失败，或控制器被强制终止，在确认清理之前会阻止重复租用。
页面显示实例 ID/标签供核对。先在 Vast 中确认对应实例已销毁、没有待确认创建，
然后由部署管理员清除 `cloud-gpu-settings` 卷中的 `rental-state.json`，再启动。
不要在实例状态不明时删除这个记录。

私有控制 API 位于 Compose 内部 8093 端口，不对宿主机发布，也不挂载 Docker socket。
主程序通过同源 `/v1/cloud-gpu` 转发控制请求；更改、启动和释放前检查全部视频已停止分析。
租用参数是经过校验的数据，不会作为任意 shell 脚本执行，凭据不放进配置或命令预览。

命令行仍支持直接管理一次云实例（此命令会实际开始租用）：

```sh
python tools/start_sam.py --gpu-name A100 --gpu-count 5 --streams 37 --disk-gb 80
```
