# 云 GPU 多路追踪

云 GPU 使用与本地部署相同的 N 路主程序结构，不再限制为一路视频。
`--streams N` 是实际创建的视频通道数，没有固定产品上限；可处理的实际路数、
采样帧率和延迟仍取决于显存、GPU 主机 CPU、内存、磁盘和网络。

本机运行控制台网关、视频接入与租用控制器。人脸 CPU 推理、事件处理、
证据编码和各路分析状态均在租用的 GPU 主机上运行，与 GPU 模型同机。
浏览器摄像头通过本机 `/ws` 原样转发到远端；RTSP/RTMP/WHEP 默认由本机拉取，
本机进行接入所需的解码与 JPEG 转发，不加载识别模型。转发连接由本机主动发起，
GPU 主机无需访问内网摄像头，也无需反向连接本机端口。
在控制台“摄像头拉流位置”或 `/gateway` 可选择“GPU 主机直接拉流”，
设置保存在本机、下次连接生效；仅选择此项时 GPU 主机才须能访问摄像头地址。
环境默认值为 `HARNESS_VIDEO_PULL_LOCATION=local`，可设为 `gpu`；保存的选择优先。
启动器按 `--streams N` 为网关预留 `64 × (N + 1) MiB` 的 `/dev/shm`，
覆盖每路 32 MiB WHEP 缓冲、进程元数据和重连期间的新旧缓冲。
直接调用 Compose 时请通过 `HARNESS_GATEWAY_SHM_SIZE` 设置相同容量（默认 128 MiB），
并确保宿主机有足够内存；`/tmp` 另保留 64 MiB 供单次分配回退。
远端断开会返回服务不可用，不会在本机启动分析。

## 启动和使用

在 `.env` 中保留现有 `VAST_API_KEY`、`HF_TOKEN`、`SAM_SSH_KEY`。
启动控制台入口，并为 GPU 主机配置 37 路分析容量：

```powershell
python tools/start_cloud_gpu.py --streams 37
```

此步骤只启动控制台，不创建付费云实例。`--dry-run` 可查看部署计划，
不会调用 Docker、租卡或修改文件。

1. 打开本机控制台。GPU 尚未启动时显示连接状态和云 GPU 租用面板。
2. 在云 GPU 区域输入型号 `A100`、数量 `5`。也可填写具体型号，例如 `A100_SXM4`。
3. 可以展开“编辑租用脚本参数”直接编辑 JSON。界面显示根据配置生成的实际启动命令。
4. 点击“启动租用（开始计费）”。页面先保存参数，再启动当次租用，等待所有 GPU 就绪。
5. 就绪后点击“打开分析控制台”，添加并连接视频，然后开始全部分析。
6. 改型号或数量前，停止全部分析，点击“释放云 GPU”，再修改和启动。

保存租用配置本身不会租卡。参数保存在 `cloud-gpu-settings` Docker 数据卷；
关闭浏览器不会释放 GPU。停止云控制器/Compose 应用会请求释放当前实例。
原 `compose.yaml` + `compose.sam31-remote.yaml` 入口也改为在 UI 明确启动租用，
其默认仍部署 1 路远端分析；多路请使用上面的启动器。
原先保存为 `legacy` 的受管云端追踪配置会自动迁移到 `cloud`；
其他本机/独立服务器设置保留。普通旧版外部单会话服务仍保留其兼容入口。

既有独立 VLM 服务的 `.env` 配置也会传到 GPU 主机的分析进程：
`INFERENCE_EXECUTION_MODE=server`、`INFERENCE_SERVER_URL`、
`INFERENCE_SERVER_MODEL`、`INFERENCE_SERVER_PROTOCOL`（`compatible` 或 `goodvision`），
以及专用的 `LOCAL_INFERENCE_API_KEY` 和 `LOCAL_INFERENCE_MAX_TOKENS`。
保存的控制台配置仍优先；VLM 地址须能从 GPU 主机访问。
服务器认证沿用专用密钥，不会使用云端供应商的 API Key 代替。

视频通道数必须与部署一致。扩容时重新用 `--streams N` 启动，
再保存云 GPU 配置中的相同路数。各路分析进程和数据目录独立，只有本机控制台开放端口。

首次升级会从原有 `camera-NN-data` 卷（旧单路入口为 `face-data`）导入配置、人脸库和记录。
新启动器创建的空 `camera-01-data` 卷不会遮住旧单路数据：第一路为空时，
从旧 `face-data` 的 `/legacy/default` 导入；已有内容的各摄像头数据优先。
升级前先停止旧分析；旧的本机 `harness-NN` 容器需停止，数据卷保留供迁移。
云 GPU 正常释放前先停止并排空所有分析进程，再通过 SSH 将数据完整同步到
`cloud-gpu-settings` 卷的 `analysis-data.tar.gz`；下次租用自动恢复。
备份失败会保留实例并报告 `cleanup_required`，实例仍会计费，应恢复连接、取回数据后释放。
断电或强制删除云实例前未同步的数据不能从旧备份恢复。模型缓存不包含在数据备份中。

## 多卡工作方式

租用查询使用精确 GPU 数量，例如 `num_gpus=5`，在一个实例上寻找五张匹配的卡。
`A100` 匹配内置 A100 PCIe/SXM4 型号列表；具体型号按输入精确查询。
没有匹配机器时会报告失败，不会改租其他型号或八张卡。
市场查询语法见 [Vast 官方 CLI](https://github.com/vast-ai/vast-cli)。

每张 GPU 启动一个模型进程，以 `CUDA_VISIBLE_DEVICES` 隔离。
视频按序号轮询分配：第 1–5 路分别使用 GPU 0–4，第 6 路回到 GPU 0。
同一路的创建、追加、健康检查、结束请求始终使用同一进程、同一通道，
模型时序状态不会跨 GPU 迁移。每张卡内部的多路会话保持独立并公平排队。
不同卡可以同时推理，启动就绪需要所有卡都通过检查。

增加 GPU 数量主要减少多路并发时共享 GPU 的排队。单路时序追踪仍在一张 GPU 上运行，
不能将五张卡的显存或计算简单合并来保证单路五倍加速。
本次修改未实际租卡或测得 A100 上的 Contour 延迟；需要用真实视频验证吞吐和延迟。

## 失败与清理

原有启动失败重试和释放流程保留。控制器持久记录本次实例 ID 和唯一租用标签。
若创建结果不明、释放失败，或控制器被强制终止，在确认清理之前会阻止重复租用。
页面显示实例 ID/标签供核对。先在 Vast 中确认对应实例已销毁、没有待确认创建，
然后由部署管理员清除 `cloud-gpu-settings` 卷中的 `rental-state.json`，再启动。
不要在实例状态不明时删除这个记录。

私有控制 API 位于 Compose 内部 8093 端口，不对宿主机发布，也不挂载 Docker socket。
网关通过同源 `/v1/cloud-gpu` 转发控制请求；释放会排空远端分析并备份数据后再销毁实例。
释放操作的控制器等待窗口为 420 秒，网关为 450 秒，浏览器为 480 秒；
等待期间释放按钮保持禁用。若最终超时，先查询实例和备份状态再处理。
租用启动/收尾期间不接受新的分析请求。`/gateway` 始终提供连接和租用状态页。
租用参数是经过校验的数据，不会作为任意 shell 脚本执行，凭据不放进配置或命令预览。

命令行仍支持直接管理一次云实例（此命令会实际开始租用）：

```sh
python tools/start_sam.py --gpu-name A100 --gpu-count 5 --streams 37 --disk-gb 80
```
