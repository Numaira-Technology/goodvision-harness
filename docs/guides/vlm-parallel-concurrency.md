# Parallel 配对调度与 48 / 72 / 96 并发测试

固定 Qwen3.5-35B-A3B（`qwen/qwen3.5-35b-a3b`），OpenRouter Alibaba 优先，
允许同模型其他供应商回退。每轮核验返回模型并记录实际供应商。模型在供应商运行，
云实例只运行 Harness、视频预览和浏览器录屏。

## 调度改动

现有 `independent` 调度继续作为默认与对照。新 `paired` 调度仅在 parallel 生效：

- 先检查 events 和 grounding 都有本地执行位置，再向两条分支提交同一个窗口 ID 和证据帧。
  其中一条本地已满，就跳过该窗口的两条分支；跳过仍计入原计划分母，不扩展测试时长补齐。
- 一条分支获得共享名额后，同视频路优先放行该窗口的另一条分支。
  各视频路之间仍按最近放行时间公平轮转，保留总并发、每路共享并发和请求发起频率限制。
- 配对等待不会被较新窗口替换；等待量受每分支本地上限约束，等待仍最多 1 秒，
  证据仍在 3 秒后过期。不会为了等待配对预占额外 HTTP 名额。
- 两条结果各自发布，快分支不等待慢分支完成。历史结果保留及最新状态防倒退逻辑继续生效。
  配对不是一次 HTTP 调用，也不保证两条原子发出：超时、取消、模型失败仍可能导致仅一条成功。

取舍：提高同窗口两条都发出/完成的机会，可能减少单独 events 的结果数量。
只有实测才能判断净收益；不承诺发出率、整体完整率一定提升。

## 固定实验

每组 12 路相同视频，默认输入 `~/Downloads/output 3.mp4`，播放 55.798021 秒。
每分支每路 1.25 Hz，计划每轮 828 个源窗口、1656 个分支任务。
模型提示词、六类判断标准、取帧、lean-v1、720 像素/JPEG 90、输出上限保持不变。
事件 HTTP 超时 5 秒，grounding HTTP 超时 20 秒；总请求发起上限 40 次/秒，源时钟错峰。
浏览器只显示目标 15 FPS 的单视频，无框、无右侧证据帧；保留逐路播放帧率诊断。
定时送帧独立于结果收集、日志与监看更新，避免集中返回的结果拖慢输入。
所有组使用同一送帧器，输入有效性仍要求没有漏送计划采样且最大送帧偏差小于 250 毫秒；
迟到输入不加速补送，失败轮次保留但不纳入有效对照。

第一轮顺序：原调度 48 → 配对 48 → 配对 72 → 配对 96。第二轮反序。
每路共享上限分别 4 / 6 / 8，本地每分支上限同步 4 / 6 / 8，避免只提高总上限。
每个正式阶段前独立预热，每个阶段独立共享调度数据库，要求前阶段排空后继续。

共 8 个正式阶段。默认上限：13248 次正式调用 + 216 次预检/预热调用 = 13464 次，
不是费用估计或保证发出数。录制预检使用模拟器，不产生 API 调用。
HTTP 401/402/403/429、模型核验失败、输入时序异常、未排空、结果留存核对失败，
或录制失败会保留已有报告并停止后续阶段。不以 3 秒作为业务达标门槛。

## 入口

在仓库根目录执行。默认离线，`--real` 才调用付费 API；`--plan-only` 不读取密钥。

```bash
python -m tools.vlm_benchmark.parallel_concurrency --plan-only

python -m tools.vlm_benchmark.parallel_concurrency \
  --cloud --real --plan-only
```

正式云端执行（替换实例信息）：

```bash
python -m tools.vlm_benchmark.parallel_concurrency \
  --real --host HOST --port PORT --identity ~/.ssh/id_ed25519_vast
```

沿用现有云运行器的隐藏密钥输入、后台运行、断线恢复、`--resume RUN_ID`、
`--stop RUN_ID` 和 `--reuse-video RUN_ID`。停止测试不会销毁租用实例。
这个固定入口不允许覆盖模型、供应商策略、视频路数或三档并发。

## 输出与判断

- `report.html`：所有阶段、录屏与各分支明细。
- `parallel-concurrency.html` / `.json` / `.csv`：每个正式阶段各自一行，包含原调度对照。
- 每轮 `reports.jsonl` 和全局 `manifest.json`：逐请求记录、源码哈希、输入哈希、参数和模型核验。

分别看 events/grounding 发出率、完整结果/计划、两条同窗口均发出率、两条均完整率。
整体延迟取同窗口两条发布延迟中的较大值，输出 P50/P95，分位数不跨轮平均。
同时保留全部 HTTP 尝试的 API 延迟、成功发出/未发出的排队等待、完成到发布等待、
错误、逐路统计、历史结果及供应商分布。

发出代表客户端进入 HTTP send，不保证服务商已收到。缺失发送标记保留为未知；
未返回、超时、未发出、只完成一条分别列示，不能互相替代。
完整结果包括合法的不确定判断，不代表识别正确率；后者仍需独立标注对照。

先对比原调度 48 与配对 48，再对比配对 48 / 72 / 96。
优先选整体完整率、逐路公平性和尾部延迟均合理的配置，不只追求发出数。
Alibaba 回退比例和时段负载可能变化，需要结合实际供应商分布解释差异。
